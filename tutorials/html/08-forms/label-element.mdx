Picture a form with three empty boxes and no words next to them. You would have no idea what to type where. Now imagine you could not see the screen, and a voice only said "edit text... edit text... edit text." That is what a form without labels sounds like to someone using a screen reader.

The `<label>` element is the **name tag** of a form field. It is small, and it is one of the most important elements in HTML forms. A correct label makes a form clearer for everyone, easier to tap on a phone, and usable with assistive technology. A missing label is the most common accessibility problem on the web, and also one of the easiest to fix.

## The Basics

A label is text that describes one form control. It is connected to that control, so the two behave as a pair.

```html title="index.html"
<label for="email">Email address</label>
<input type="email" id="email" name="email" />
```

</TabItem>

</form>

The connection comes from two matching values:

| On the label | On the field | Meaning |
| :-- | :-- | :-- |
| `for="email"` | `id="email"` | "This label belongs to the field whose id is `email`" |

:::info Note the difference
- **`id`** identifies the field **on the page**, so a label (or CSS or JavaScript) can point at it.
- **`name`** is the key under which the value is **sent to the server**.

They are often the same word, but they do different jobs. A label uses `for` and `id`, never `name`.
:::

## Two Ways to Connect a Label

### 1. Explicit: `for` and `id`

The label and the field sit separately, and are linked by matching attributes.

```html
<label for="city">City</label>
<input type="text" id="city" name="city" />
```

- Works even when the label and field are far apart in the layout.
- Is the **most flexible** and the most widely recommended method.
- Each `id` on the page must be **unique**.

### 2. Implicit: Wrapping

The field is placed **inside** the label. No `for` or `id` is needed.

```html
<label>
  City
  <input type="text" name="city" />
</label>
```

- Quick to write, and common for checkboxes and radio buttons.
- Slightly harder to style when the label text and field must sit in separate columns.

### Using Both

For the best support in all tools, you can combine them. This is harmless, and useful when you are not sure how a tool handles wrapping:

```html
<label for="city">
  City
  <input type="text" id="city" name="city" />
</label>
```

:::tip Which should I use?
Use **explicit** (`for` and `id`) for text fields, and either for checkboxes and radio buttons. If you pick one method and use it consistently, your forms stay easy to maintain.
:::

## What a Label Gives You

### 1. A Bigger Click Target

Clicking or tapping a label **activates its field**: it puts the cursor in a text box, toggles a checkbox, or selects a radio button. This is a big help on phones, where a tiny checkbox is hard to hit.

Try it. Click the words next to each box:

<BrowserWindow url="http://127.0.0.1:5500/index.html">
<>
<ClickDemo />
</>
</BrowserWindow>

The first box responds to a click on its text because of the label. The second does not, because it has none.

### 2. An Accessible Name

Assistive technology reads the label as the field's **name**. For the email field above, a screen reader says:

> "Email address, edit text, required."

Without a label, it says only "edit text," and the user cannot tell what to enter.

### 3. Voice Control

People who control their computer by voice can say "click Email address" to reach the field. That works only if the field has a label with visible text that matches.

### 4. Better Searching and Testing

Tools that test or automate forms often find fields by their label text, so labeled forms are easier to maintain.

:::note Accessibility rule (WCAG)
Every form control needs a programmatic **label or name** (WCAG success criterion "Labels or Instructions" and "Name, Role, Value"). It is one of the clearest rules in accessibility, and a missing label is the easiest failure to prevent.
:::

## A Placeholder Is Not a Label

The `placeholder` attribute shows faint text inside an empty field. It looks like a label, which makes it a tempting shortcut. Do not use it as one.

<Tabs>
<TabItem value="bad" label="Placeholder only" default>

```html
<input type="email" name="email" placeholder="Email address" />
```

</TabItem>
<TabItem value="good" label="Label plus placeholder">

```html
<label for="email">Email address</label>
<input
  type="email"
  id="email"
  name="email"
  placeholder="name@example.com"
/>
```

</TabItem>
</Tabs>

| Problem with placeholder-only fields | Why it matters |
| :-- | :-- |
| **It disappears** when the user starts typing | They forget what the field was for, especially in long forms |
| **Low contrast** by default | Hard to read for many people |
| **Not always announced** as the field's name | Support in assistive technology is inconsistent |
| **Looks "already filled in"** | Some users think the field is done and skip it |
| **Cannot be clicked** to focus the field | No bigger target |
| **Often cut off** in other languages | Translated text can be longer |

The right use for a placeholder is a short **example of the format**, such as `name@example.com`. Never use it for the field's name or for instructions that people need to keep seeing.

### "Floating Labels"

A popular design shows the label inside the field and moves it above as the user types. Done well, it is fine, because the label **stays in the HTML** and remains visible. Done badly, it is a placeholder in disguise. If you use floating labels, test them with a screen reader and at high zoom.

## Hiding a Label (Carefully)

Sometimes a design shows a field with no visible label, such as a search box next to a magnifier button. The field **still needs a label** for assistive technology. There are three acceptable ways.

### Option 1: A Visually Hidden Label (best)

Keep a real `<label>`, and hide it **from the eye only**, using a CSS class:

```css title="style.css"
.visually-hidden {
  position: absolute;
  width: 1px;
  height: 1px;
  margin: -1px;
  padding: 0;
  overflow: hidden;
  clip: rect(0 0 0 0);
  white-space: nowrap;
  border: 0;
}
```

<Tabs>
<TabItem value="code" label="HTML Code" default>

```html title="index.html"
<form action="/search" method="get" role="search">
  <label for="q" class="visually-hidden">Search the site</label>
  <input type="search" id="q" name="q" placeholder="Search..." />
  <button type="submit">Go</button>
</form>
```

</TabItem>
<TabItem value="output" label="Browser Output">

<BrowserWindow url="http://127.0.0.1:5500/index.html">
<>
<form action="/search" method="get" role="search" onSubmit={(event) => event.preventDefault()}>
  <label htmlFor="lbl-q" style={visuallyHidden}>Search the site</label>
  <input type="search" id="lbl-q" name="q" placeholder="Search..." />{" "}
  <button type="submit">Go</button>
</form>
</>
</BrowserWindow>

</TabItem>
</Tabs>

The label is invisible on screen, but a screen reader announces "Search the site, search edit text." Sighted users get a visual clue from the button and the placeholder.

### Option 2: `aria-label`

Put the name straight on the field:

```html
<input type="search" name="q" aria-label="Search the site" />
```

Simple, but it has no visible text, so voice control users and people who translate the page may miss it.

### Option 3: `aria-labelledby`

Point the field at text that already exists on the page:

```html
<h2 id="search-title">Search</h2>
<input type="search" name="q" aria-labelledby="search-title" />
```

:::warning Hide with care
Do **not** hide a label with `display: none` or `visibility: hidden`, or the `hidden` attribute. That removes it from assistive technology too, and the field is nameless again. Use the visually hidden technique above.
:::

## Labels for Checkboxes and Radio Buttons

For these controls, the label sits **beside** the box, and is usually written by wrapping.

Each radio button has its **own** label ("Beginner," "Advanced"). A `<label>` names one control. A `<legend>` names a group.

## Which Elements Can Have a Label?

A label can be connected to any **labelable** element:

| Labelable | Example |
| :-- | :-- |
| `<input>` (except `type="hidden"`) | Text, email, checkbox, radio, file... |
| `<textarea>` | A message box |
| `<select>` | A drop-down |
| `<button>` | Gets its name from its own text, but a label works too |
| `<meter>` and `<progress>` | Gauges and progress bars |
| `<output>` | A calculated result |

An `<input type="hidden">` has no visible control, so it needs no label.

## Hints, Required Markers, and Errors

A label gives the **name**. Extra help belongs in separate text that is **connected** to the field.

<Tabs>
<TabItem value="code" label="HTML Code" default>

```html title="index.html"
<label for="pw">Password</label>
<input
  type="password"
  id="pw"
  name="password"
  autocomplete="new-password"
  aria-describedby="pw-hint"
  required
/>
<p id="pw-hint">At least 12 characters. A short sentence works well.</p>
```

</TabItem>
<TabItem value="output" label="Browser Output">

<BrowserWindow url="http://127.0.0.1:5500/index.html">
<>
<form onSubmit={(event) => event.preventDefault()}>
  <label htmlFor="lbl-pw">Password</label><br />
  <input
    type="password"
    id="lbl-pw"
    name="password"
    autoComplete="new-password"
    aria-describedby="lbl-pw-hint"
    required
  />
  <p id="lbl-pw-hint" style={{ marginTop: "0.25rem", fontSize: "0.9rem" }}>
    At least 12 characters. A short sentence works well.
  </p>
</form>
</>
</BrowserWindow>

</TabItem>
</Tabs>

`aria-describedby` points at the hint's `id`. A screen reader reads the label first ("Password"), then the field type, then the hint. The same trick connects **error messages** to fields, which you will see in [Accessible Forms](./accessible-forms).

### Marking Required Fields

If a field is required, say so in the label, and use the `required` attribute too.

```html
<label for="name">Full name <span aria-hidden="true">*</span></label>
<input type="text" id="name" name="name" required />
```

Whatever symbol you pick, **explain it** near the top of the form ("* means required"), or write "(required)" in words. Do not use color alone.

| Approach | Notes |
| :-- | :-- |
| "Full name (required)" | The clearest, and the easiest to translate |
| `*` with a note "* required" | Common, but explain it |
| Marking the optional fields instead, "(optional)" | Good when most fields are required |
| Red label color only | Not enough on its own |

## Writing Good Label Text

1. **Be short and clear.** "Email address," not "Please enter the email address that you use."
2. **Name the content, not the control.** "Email," not "Text box 1."
3. **Be specific.** "Delivery postcode" beats "Code."
4. **Put the label near the field,** usually above it, or beside it for checkboxes. Above-field labels also fit narrow phone screens best.
5. **Use sentence case,** and no ending colon is needed.
6. **Do not rely on position alone.** Label text must make sense when heard by itself.
7. **Match the label to the field's purpose,** so that `autocomplete` and voice control work.

## Do Not Put Interactive Content Inside a Label

A label is itself clickable, so nesting other interactive elements inside it causes confusion.

<Tabs>
<TabItem value="bad" label="Risky" default>

```html
<label for="terms">
  I accept the <a href="/terms">terms and conditions</a>
</label>
<input type="checkbox" id="terms" name="terms" />
```

</TabItem>
<TabItem value="good" label="Safer">

```html
<input type="checkbox" id="terms" name="terms" />
<label for="terms">I accept the terms and conditions</label>
<a href="/terms">Read the terms</a>
```

</TabItem>
</Tabs>

In the risky version, clicking the link and clicking the label do different things in the same spot, and it is easy to tick the box by accident when trying to follow the link. Many sites do use links inside labels, so it is not forbidden, but a separate link is clearer and safer.

## Styling Labels

A label is a normal inline element. Common styles:

```css title="style.css"
label {
  display: block;            /* put the label above the field */
  font-weight: 600;
  margin-bottom: 0.25rem;
}

.checkbox-label {
  display: flex;             /* box and text side by side */
  align-items: center;
  gap: 0.5rem;
  cursor: pointer;
}
```

A pointer cursor on clickable labels is a small hint that the label is active.

## Global Audience Notes

- **Write labels in the page's language,** and set the `lang` attribute.
- **Keep them short.** Translations can run much longer, and long labels wrap badly in narrow layouts.
- **Do not build sentences from separate pieces** (for example, a label before a field and a unit after it that together form a sentence), because word order differs between languages.
- **Avoid slang and idioms,** since translation tools handle plain words best.
- **Be careful with "name" fields.** "Full name" or "Name" suits more cultures than "First name" and "Last name."
- **Leave room.** Labels in some languages may be much longer than in English.

## Common Mistakes to Avoid

1. **No label at all.** The most common and most serious mistake.
2. **A `for` that does not match any `id`,** so the label is connected to nothing.
3. **Duplicate `id` values** on the page, so labels point to the wrong field.
4. **Using the placeholder as the label.**
5. **Using `name` in `for`.** It must match the `id`.
6. **Hiding labels with `display: none`.** It removes them from screen readers.
7. **One label for a whole group** of radio buttons. Use `<fieldset>` and `<legend>`.
8. **Putting a long paragraph inside a label.** Move extra help to `aria-describedby` text.
9. **Using `<p>` or `<span>` in place of `<label>`.** It looks the same, but it is not connected.
10. **Wrong order of text and fields** that makes the label ambiguous (for example, a label between two fields).

## Key Takeaways

- Every form control needs a label. A missing one is the most common form accessibility failure.
- Connect a label with `for` and a matching `id`, or by wrapping the control. Never use `name` in `for`.
- Labels enlarge the click and tap target, give fields an accessible name, and support voice control.
- A placeholder is not a label. Use it only for a format example.
- If a design hides a label, hide it visually with CSS, never with `display: none`.
- Put hints and errors in separate text linked with `aria-describedby`, and mark required fields in words, not by color alone.
- Write short, plain labels that translate well.
