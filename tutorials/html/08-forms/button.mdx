Buttons are how pages **do** things: send a form, open a menu, add to a basket, play a video. In [Submit and Reset Buttons](./input-types/submit-reset-button), you met three button-like `<input>` types. HTML also has a dedicated **`<button>` element** that does the same jobs, and more. Most modern code prefers it, because a button can hold **anything**: text, an icon, an image, even styled spans.

It is a simple element with one famous trap: **a `<button>` inside a form submits the form by default**, even if you did not mean it to. In this lesson, you will learn the three types, how to send a stable `name` and `value`, how to build icon and toggle buttons, and how to make them accessible.

The label is the **content between the tags**, not a `value` attribute. And, unlike `<input>`, `<button>` needs an **end tag**.

## Button or Input?

| | `<button>` | `<input type="submit">` |
| :-- | :-- | :-- |
| **Label** | Content between the tags | The `value` attribute |
| **Content** | Text, icons, images, `<span>`, `<strong>`, `<em>`... | Plain text only |
| **Stable `value`** | Yes: label and value are separate | No: the label **is** the value |
| **Pseudo-elements** (`::before`, `::after`) | Yes | No |
| **Types** | `submit`, `reset`, `button` | `submit`, `reset`, `button`, `image` |
| **Best for** | Almost everything | Very simple forms, or older code |

Use `<button>` unless you have a reason not to.

## The `type` Attribute

A button has three types, and one of them is the **default**.

| Type | What it does when clicked |
| :-- | :-- |
| `submit` | Checks and **sends the form**. This is the default |
| `reset` | Puts every field back to its **starting** value |
| `button` | **Nothing** by itself. Use it with JavaScript |

:::danger The default type is `submit`
A `<button>` with **no `type`** inside a form is a **submit** button. So a button meant for "Show password," "Add row," or "Preview" will **send the form** when clicked, unless you write `type="button"`. This is one of the most common bugs in forms.

```html
<button>Show password</button>              <!-- BUG: submits the form -->
<button type="button">Show password</button> <!-- correct -->
```

**Always write `type` on every button**, even `type="submit"`. It costs nothing, and it states your intention.
:::

Outside any form, a button does nothing until JavaScript gives it a job, so the type matters only inside forms. But the habit is still good.

## Name and Value: Several Actions in One Form

Like a submit input, a `<button>` with a `name` adds its `name=value` to the data, but **only when it is the one clicked**. With `<button>`, though, the **label and the value are separate**, which solves a real problem.

Switch the page language, and press a button. The **label** changes ("Save draft" or "ड्राफ्ट सहेजें"), but the server always receives `action=save` or `action=publish`. With `<input type="submit">`, the translated label would have been sent, and your server code would break.

So: **show any text you like, and send a stable code.**

### The `form*` Attributes

A `<button type="submit">` accepts the same overrides as a submit input:

| Attribute | Overrides |
| :-- | :-- |
| `formaction` | The form's `action` |
| `formmethod` | The form's `method` |
| `formenctype` | The form's `enctype` |
| `formtarget` | The form's `target` |
| `formnovalidate` | Skips validation for this click |

```html
<button type="submit">Publish</button>
<button type="submit" formaction="/drafts" formnovalidate>Save draft</button>
```

Remember: when a visitor presses `Enter` in a text field, the browser clicks the form's **first** submit button. Put the main action first.

## What Can Go Inside a Button

A button holds **phrasing content**: text and inline elements.

```html
<!-- Text with emphasis -->
<button type="submit">Pay <strong>$49</strong> now</button>

<!-- Icon and text -->
<button type="button">
  <svg aria-hidden="true" width="16" height="16"><!-- icon --></svg>
  <span>Download</span>
</button>

<!-- An image -->
<button type="button">
  <img src="cart.svg" alt="" width="20" height="20" /> Add to basket
</button>
```

Rules:

- **No interactive content inside a button.** Do not nest a link (`<a>`), another button, an input, or a select. It is invalid, and it behaves unpredictably.
- **No block layout** (`<div>`, `<p>`, headings). Use `<span>` and inline elements, and use CSS to lay them out.
- Decorative icons get `aria-hidden="true"` (SVG) or `alt=""` (image), so screen readers read only the text.

### Icon-Only Buttons

A button with only an icon needs a **text name**, or it is a silent button to a screen reader:

```html
<!-- Option 1: a visually hidden text -->
<button type="button">
  <svg aria-hidden="true" width="20" height="20"><!-- trash icon --></svg>
  <span class="visually-hidden">Delete comment</span>
</button>

<!-- Option 2: aria-label -->
<button type="button" aria-label="Delete comment">
  <svg aria-hidden="true" width="20" height="20"><!-- trash icon --></svg>
</button>
```

Either works. Hidden text translates more easily, and also helps people who use browser translation. Also add a **tooltip** or a visible label when the icon is not universally understood, because many icons mean different things to different people.

## Toggle Buttons: `aria-pressed`

Some buttons switch something on and off: "Favourite," "Mute," "Bold." These are **toggle buttons**. Screen readers need to know the **state**, and `aria-pressed` provides it.

<Tabs>
<TabItem value="code" label="HTML Code" default>

```html title="index.html"
<button type="button" id="fav" aria-pressed="false">☆ Favourite</button>
<span id="status" role="status">Not a favourite.</span>

<button type="button" id="save">Save changes</button>
```

```js title="script.js"
const fav = document.getElementById("fav");
const status = document.getElementById("status");

fav.addEventListener("click", () => {
  const on = fav.getAttribute("aria-pressed") !== "true";
  fav.setAttribute("aria-pressed", String(on));
  fav.textContent = (on ? "★" : "☆") + " Favourite";
  status.textContent = on ? "Added to favourites." : "Not a favourite.";
});

const save = document.getElementById("save");
save.addEventListener("click", () => {
  save.disabled = true;
  save.setAttribute("aria-busy", "true");
  save.textContent = "Saving...";

  setTimeout(() => {
    save.disabled = false;
    save.removeAttribute("aria-busy");
    save.textContent = "Save changes";
  }, 1500);
});
```

Key points:

- **`aria-pressed="true" or "false"`** means "this is a toggle, and it is on (or off)." Screen readers say "Favourite, toggle button, pressed."
- **Keep the label the same** when the state changes. Here, "Favourite" stays, and only the star changes. If the text changes from "Mute" to "Unmute" **and** you use `aria-pressed`, the state is confusing. Use one approach: a fixed label with `aria-pressed`, **or** a changing label with no `aria-pressed`.
- For a button that **opens or closes** something (a menu, an accordion), use **`aria-expanded`** (and `aria-controls`) instead.
- Announce the result in a `role="status"` region when the change is not otherwise visible.

## Loading and Disabled States

### During a Request

While a request is running, tell the visitor, and stop repeat clicks:

- Set the label to "Saving..." (or show a spinner next to text).
- Set **`aria-busy="true"`**.
- Block extra clicks: use `disabled`, or ignore clicks while a flag is on.
- Return the button to normal when the request ends, even if it fails.

### `disabled` and `aria-disabled`

| | `disabled` | `aria-disabled="true"` |
| :-- | :-- | :-- |
| Clickable? | **No** (clicks are blocked by the browser) | **Yes**, unless your code ignores the click |
| Focusable with `Tab`? | **No** | **Yes** |
| Sent as a submitter? | No | Yes, if clicked, so guard it in JavaScript |
| Screen reader | Announced as "dimmed" or "unavailable" | Announced as "dimmed," and still found |
| Good for | Short busy states, or things that truly cannot be used | Buttons whose **reason** must be discoverable |

Think carefully before disabling a submit button until a form is valid. The visitor cannot find out why it does not work, and keyboard users cannot even reach it. It is usually better to leave it enabled, and show clear messages on click. See [Submit and Reset Buttons](./input-types/submit-reset-button).

If you use `aria-disabled`, your own code must **stop the action** (check the attribute in the click handler), because the browser will still run it.

## Button or Link?

A very common question, with a clear answer:

| The element... | Use |
| :-- | :-- |
| **Goes somewhere** (another page, a section, a file, an email) | A **link**: `<a href="...">` |
| **Does something** on the page (submits, opens a dialog, toggles, adds, deletes) | A **button**: `<button type="button">` |

```html
<a href="/pricing">See pricing</a>                 <!-- navigation: a link -->
<button type="button">Open the menu</button>        <!-- action: a button -->
```

Do not use `<a href="#" onclick="...">` for actions, and do not use a `<button>` that sets `location.href` for navigation. Links and buttons are announced differently, behave differently (a link can be opened in a new tab, bookmarked, and copied), and respond to different keys.

And never build a button from a `<div>` or `<span>` with a click handler. You would have to rebuild the focus, the keyboard (`Enter` **and** `Space`), the role, and form behaviour yourself. The real `<button>` gives you all of it for free.

## Popover and Other Newer Features

Modern HTML adds **declarative** buttons that control other elements, with no JavaScript. For example, the `popovertarget` attribute opens a **popover**:

```html
<button type="button" popovertarget="tips">Show tips</button>
<div id="tips" popover>Use a strong, long password.</div>
```

Support is good in current browsers, but still new. Check that it works for your audience, and test the keyboard and screen reader behaviour. The `<dialog>` element works with a `<button>` and a small script, too.

## Styling a Button

```css title="style.css"
button {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  gap: 0.5rem;                   /* space between an icon and text */
  min-height: 2.75rem;           /* a comfortable tap target */
  padding: 0.6rem 1.25rem;
  border: 1px solid #2563eb;
  border-radius: 6px;
  background: #2563eb;
  color: #fff;
  font: inherit;
  font-weight: 600;
  line-height: 1.2;
  cursor: pointer;
}

button:hover {
  background: #1d4ed8;
}

button:active {
  transform: translateY(1px);
}

button:focus-visible {
  outline: 3px solid #1e3a8a;
  outline-offset: 2px;
}

button:disabled,
button[aria-disabled="true"] {
  opacity: 0.6;
  cursor: not-allowed;
}

/* A quieter secondary button */
button.secondary {
  background: transparent;
  color: #2563eb;
}
```

- **`font: inherit`** stops the button from using a small system font.
- Give buttons at least **44 pixels** of height, and enough space between them.
- Keep **contrast** high: at least 4.5:1 for the text, and 3:1 for the button's border or background against the page.
- Always keep a visible **focus** style.
- Make the **main** action look strongest, and secondary actions quieter. Do not make a dangerous button (Delete) look like the safe one.
- For a pending state, do not rely on **colour** alone. Change the text too.

## Accessibility at a Glance

- **Use a real `<button>`.** You get keyboard support (`Enter` and `Space`), the right role, and focus handling for free.
- **Write a clear name:** "Add to basket," "Delete comment." Avoid "Click here" and "Submit." The name should make sense on its own, even in a list of buttons.
- **Give every icon-only button** a text name (hidden text or `aria-label`).
- **Show state** with `aria-pressed` (toggle), `aria-expanded` (opens something), and `aria-busy` (working).
- **Do not rely on colour alone** to tell buttons apart or to show a state.
- **Keep the focus** visible, and make the target at least about 44 by 44 pixels, with space around it.
- **Announce results** of an action (saved, added, deleted) in a `role="status"` region, and move focus only when needed (for example, to a dialog).
- **Do not disable the submit button** just to show the form is incomplete.
- **Keep the same name** for the same action everywhere, so the page is predictable.
- **Never put a link inside a button,** or a button inside a link.

## Security and Validation Notes

- **Browser checks can be skipped.** Whatever a button sends (`action=delete`), anyone can send by hand. The server must check **who** is asking, and whether they may do it.
- **Allow-list the button values** (`save`, `publish`) on the server, and reject the rest.
- **Protect actions that change things** (delete, pay, change email) with a CSRF token and `method="post"`, and never with a link or a `GET` request.
- **Confirm destructive actions** ("Delete this account?"), and make them reversible where you can.
- **Guard against double clicks** in the browser, and also on the server.

See [Secure Form Design](./secure-form-design).

## Global Audience Notes

- **Keep labels short and action-based.** They translate best, and fit in narrow buttons. Remember that translated text can be **40 percent longer**, so do not use a fixed width.
- **Do not send the label as the value.** Use a stable `value`, as in the language demo.
- **Do not rely on icons** alone. A tick, a heart, a trash can, or a hand may mean different things in different cultures.
- **Right-to-left languages** flip the order of icon and text automatically when you use `flex` and `dir="rtl"`. Check that arrows ("Next") still point the right way (use logical CSS or mirror them).
- **Mind the order of buttons** in dialogs. "OK" and "Cancel" appear in different orders on different systems. Keep it consistent within your site.

## Common Mistakes to Avoid

1. **Forgetting `type="button"`** on a non-submit button inside a form, so it submits.
2. **Leaving off `type`** entirely. Always write it.
3. **Sending the label as the value** with `<input type="submit">`, and breaking when it is translated.
4. **Using a `<div>` or `<span>`** as a button.
5. **Using a link for an action,** or a button for navigation.
6. **An icon-only button** with no accessible name.
7. **Putting a link, input, or another button inside a button.**
8. **Changing both the label and `aria-pressed`** on a toggle.
9. **Disabling the submit button** until the form is valid.
10. **Using `aria-disabled` without stopping the click** in JavaScript.
11. **No loading state or double-submit protection.**
12. **Trusting the button's value** on the server without checking permission.

<details>
<summary>1. What is the default `type` of a `<button>`?</summary>

`submit`. A button with no `type` inside a form submits the form. Write `type="button"` for buttons that should not submit, and write `type` on every button.

</details>

<details>
<summary>2. Why is `<button>` better than `<input type="submit">` for several actions?</summary>

Its label and value are separate. You can translate or restyle the label while still sending a stable value such as `action=publish`. It can also hold icons and formatted text.

</details>

<details>
<summary>3. What can and cannot go inside a button?</summary>

Text, inline elements (`<span>`, `<strong>`, `<img>`, SVG) are fine. Interactive content (links, inputs, other buttons) and block layout elements are not allowed.

</details>

<details>
<summary>4. How do you name an icon-only button?</summary>

Add visually hidden text inside it, or `aria-label="Delete comment"`, and hide the decorative icon with `aria-hidden="true"`.

</details>

<details>
<summary>5. What is the difference between `disabled` and `aria-disabled="true"`?</summary>

`disabled` blocks clicks and removes the button from the tab order. `aria-disabled` only announces the state: the button can still be focused and clicked, so your code must stop the action.

</details>

<details>
<summary>6. When should you use a link, and when a button?</summary>

A link (`<a href>`) goes somewhere: another page, a section, or a file. A button does something on the page: submits, toggles, opens, adds, or deletes.

</details>

## Key Takeaways

- `<button>` is the flexible, preferred button element. Its label is its content, and it can hold text, icons, and images.
- The default type is **`submit`**, so always write `type="button"` for non-submitting buttons, and write `type` on all of them.
- A button's `name` and `value` are sent only when it is clicked, and the value stays stable while the label changes, which makes it ideal for multi-action forms and translations.
- Name icon-only buttons, show state with `aria-pressed`, `aria-expanded`, and `aria-busy`, and avoid disabling buttons without a reason.
- Use links to go somewhere, and buttons to do something. Never fake a button with a `div`.
- Style with `font: inherit`, large targets, high contrast, and a visible focus, and validate and authorise every action on the server.
