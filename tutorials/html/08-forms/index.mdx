Everything you have built so far is **one-way**: you publish, and visitors read. Forms turn the web into a **conversation**. They are how a visitor signs up, logs in, searches, orders a book, leaves a comment, books a seat, or tells you what they think. Nearly every useful website has at least one.

Forms are also where HTML meets the real world. People make typos, use screen readers, type on small phones, speak different languages, and sometimes try to break things on purpose. A good form handles all of that gracefully. This section teaches you how to build forms that are **clear, easy to complete, accessible to everyone, and safe**.

## What You Will Learn

In this section, you will be able to:

- Build a form with the **`<form>` element** and decide where its data goes
- Choose between the **GET and POST** methods
- Create fields with **`<input>`** and name them with **`<label>`**
- Pick the right **input type** for emails, numbers, dates, passwords, files, and more
- Collect longer text with **`<textarea>`** and choices with **`<select>`**, **`<option>`**, and **`<datalist>`**
- Add **buttons** and group related fields with **`<fieldset>` and `<legend>`**
- Help users with **`autocomplete`**
- Check data in the browser with **`required`, `min`, `max`, `minlength`, `maxlength`, and `pattern`**
- Send files with **multipart form data**
- Make forms **accessible** and **secure**

## How a Form Works

A form is a **round trip**:

```text
1. The visitor fills in the fields
        │
        ▼
2. The browser checks the data       (required, type, pattern, min, max ...)
        │   problems? → the visitor fixes them
        ▼
3. The visitor presses Submit
        │
        ▼
4. The browser packs the data into name=value pairs
   and sends them to the address in  action  using the  method
        │
        ▼
5. A server receives, checks again, and acts   (saves, replies, redirects)
        │
        ▼
6. The visitor sees a result page or message
```

Two important points sit in that picture:

- HTML creates the form and does the **first** check (step 2). It does **not** store or process anything by itself. A **server** does that (step 5), written in a language such as Node.js, Python, PHP, or Java.
- The browser's check is a **convenience**, not security. Anyone can bypass it. The server **must always check again**. You will learn why in [Secure Form Design](./forms/secure-form-design).

## The Parts of a Form

| Part | Element | What it does |
| :-- | :-- | :-- |
| The container | `<form>` | Wraps the fields, and says where and how to send them |
| A field | `<input>`, `<textarea>`, `<select>` | Where the visitor types or chooses |
| A name tag | `<label>` | Tells people (and tools) what a field is for |
| A group | `<fieldset>` and `<legend>` | Groups related fields under a title |
| An action | `<button>` | Submits, resets, or runs something |
| A helper | `<datalist>` | Suggests values while typing |

### The Two Attributes Every Field Needs

Almost every field depends on two attributes. If you remember nothing else, remember these:

| Attribute | Used for | What happens without it |
| :-- | :-- | :-- |
| **`name`** | The key under which the field's value is **sent** to the server | The value is **not sent at all** |
| **`id`** | Linking a `<label>` to the field with `for` | The label is not connected, which breaks accessibility and click-to-focus |

```html
<label for="email">Email</label>
<input type="email" id="email" name="email" />
```

When the form is submitted, the browser sends `email=ada@example.com`. The `name` is the key, and what the visitor typed is the value.

## Choosing the Right Control

Picking the right control saves visitors effort, and often prevents mistakes before they happen.

| Situation | Best control | Why |
| :-- | :-- | :-- |
| 2 to 5 options, only one allowed | Radio buttons | All options are visible at once |
| 6 to about 15 options, only one allowed | `<select>` | Saves space |
| Many options, or the user may know the answer already | Text input with `<datalist>` | Suggestions plus free typing |
| Several options allowed | Checkboxes | Clear and simple |
| Agree or not | A single checkbox | The standard pattern |
| A short answer | `<input>` | One line |
| A comment, message, or address | `<textarea>` | Room to write |

## What Makes a Good Form?

Think of it as a short conversation with a stranger. You want it to be polite, quick, and clear.

1. **Ask only what you need.** Every extra field makes people leave.
2. **Label every field,** visibly and correctly.
3. **Use the right control,** so the phone shows the right keyboard.
4. **Help before correcting.** Show format hints, and use `autocomplete`.
5. **Validate kindly.** Say what is wrong and how to fix it, in plain words.
6. **Work with a keyboard** alone, and with a screen reader.
7. **Work on a small screen,** with big enough touch targets.
8. **Keep it safe.** Check everything again on the server, and protect personal data.
9. **Confirm success.** Tell people clearly that their message was received.

## Common Beginner Mistakes

| Mistake | What goes wrong | Where you will fix it |
| :-- | :-- | :-- |
| Fields with no `name` | Their data is never sent | [Input Element](./forms/input-element) |
| Using the placeholder as the label | The hint vanishes when typing, and screen readers may skip it | [Label Element](./forms/label-element) |
| Clicking a label does nothing | `for` and `id` do not match | [Label Element](./forms/label-element) |
| Using `type="text"` for everything | No helpful keyboard, no free validation | [Input Types](./forms/input-types) |
| Using GET for passwords | They appear in the address bar and logs | [Form Methods](./forms/form-methods) |
| A `<button>` inside a form that submits by accident | Missing `type="button"` | [Button](./forms/button) |
| Unclear error messages | People give up | [Form Validation](./forms/form-validation) |
| Relying only on browser checks | Anyone can bypass them | [Secure Form Design](./forms/secure-form-design) |
| No `enctype` on a file upload | Only the file's name is sent | [Multipart Form Data](./forms/multipart-form-data) |
| Using red color alone to show errors | Colorblind users cannot tell | [Accessible Forms](./forms/accessible-forms) |

## Forms for a Global Audience

People everywhere will use your form. Small decisions decide whether it works for them.

- **Names are not "first" and "last."** Many people have one name, several family names, or a different order. A single "Full name" field is often kinder, and avoid forcing a pattern.
- **Addresses differ.** Not every country has states or ZIP codes. Allow flexible fields, and do not require a field that may not exist.
- **Phone numbers vary.** Allow a country code, spaces, and dashes. Do not reject a valid format.
- **Dates and numbers vary.** `<input type="date">` lets the browser show the person's own format. Be careful with `pattern` rules built for one country.
- **Use `autocomplete`** tokens, so browsers fill in details in the person's language.
- **Allow longer text.** Names and addresses in some languages are longer than you expect, and may include accents and non-Latin characters.
- **Set `lang`** on the page, and write labels and messages in plain, short words that translate well.
- **Mind data laws.** Rules about collecting personal data (such as GDPR in Europe) apply to visitors from those regions. Collect the minimum, say why, and let people ask for deletion.

## A Note on Security Before You Start

Every field you add is a **door** into your system. People on the internet will try the handle. As you work through this section, keep three rules in mind:

1. **Never trust data from the browser.** Always validate and clean it on the server.
2. **Use POST (over HTTPS)** for anything private, and never send passwords by GET.
3. **Collect only what you need,** and protect it.

You will study each of these in depth in [Form Methods](./forms/form-methods) and [Secure Form Design](./forms/secure-form-design).

## Quick Recap

Test yourself. Click a question to reveal the answer.

<details>
<summary>1. Which element wraps all the fields of a form?</summary>

The `<form>` element. Its `action` says where to send the data, and its `method` says how.

</details>

<details>
<summary>2. Which attribute decides the key under which a field's value is sent?</summary>

`name`. A field with no `name` is not sent at all.

</details>

<details>
<summary>3. Which two attributes connect a label to its field?</summary>

`for` on the `<label>` must match `id` on the field. You can also wrap the field inside the `<label>`.

</details>

<details>
<summary>4. Does HTML store the data that visitors submit?</summary>

No. HTML only builds the form and sends the data. A server-side program receives, checks, and stores it.

</details>

<details>
<summary>5. Why must a server check the data again, even if the browser already did?</summary>

Browser checks are a convenience, and anyone can bypass them. The server is the only place where checks can be trusted.

</details>

<details>
<summary>6. When would you pick radio buttons over a select list?</summary>

When there are only a few options (about two to five) and only one may be chosen, so everything is visible at once.

</details>

## Key Takeaways

- A form is a conversation: fields collect data, the browser does a first check, and a server does the real work.
- `<form>` holds the fields. `action` and `method` decide where and how the data is sent.
- Give every field a `name` (so it is sent) and a matching `<label>` (so it is understood).
- Pick the right control and input type, and use `required`, `min`, `max`, `minlength`, `maxlength`, and `pattern` to guide people.
- Build for everyone: keyboard, screen reader, small screen, and any language or region.
- Never trust the browser. Check on the server, use POST over HTTPS for private data, and collect only what you need.
