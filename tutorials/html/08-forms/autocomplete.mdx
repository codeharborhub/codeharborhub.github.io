    <form onSubmit={(event) => event.preventDefault()}>
      <p style={{margin: "0 0 0.6rem"}}>

          ))}
        </select>
      </p>
      <pre style={{margin: 0, whiteSpace: "pre-wrap"}}><code>{code}</code></pre>
    </form>
  );

You have probably used this without noticing. You tap a field, your phone offers your email address, and one tap fills it in. Or your password manager fills a login form in a second. That is **autofill**, and the HTML attribute that guides it is **`autocomplete`**.

Good use of `autocomplete` makes forms **faster to fill in, easier to use, and more accessible**, especially on phones, and for people who find typing hard. Bad use (or switching it off without thinking) makes visitors retype the same details again and again. This lesson shows you how to do it well.

## The Basics

`autocomplete` tells the browser **what kind of information** a field wants, so it can offer saved values for it.

If your browser has saved details, tapping a field offers them, and the browser may fill **several fields at once**. What it offers depends on the browser and on what the visitor has saved, so you may not see suggestions in a fresh browser.

:::note What autocomplete is not
- It does **not** validate anything.
- It is **not** the same as [`<datalist>`](./datalist), which shows suggestions **you** provide.
- It does **not** send anything differently. The submitted value is just what is in the field.
:::

## The Values You Can Use

The attribute takes a **token** (a keyword) from a fixed list. Here are the ones you will use most.

### Names and contact

| Token | For |
| :-- | :-- |
| `name` | The full name |
| `given-name` | First name |
| `family-name` | Last name |
| `additional-name` | Middle name |
| `honorific-prefix` | Title, like Dr or Ms |
| `nickname` | A nickname |
| `email` | Email address |
| `tel` | Full phone number with country code |
| `tel-national` | Phone number without the country code |
| `organization` | Company or organisation |
| `organization-title` | Job title |
| `bday` | Birthday (with `type="date"`) |
| `url` | A website |

### Addresses

| Token | For |
| :-- | :-- |
| `street-address` | The whole street address, in one multi-line field |
| `address-line1`, `address-line2`, `address-line3` | Separate address lines |
| `address-level2` | City or town |
| `address-level1` | State, province, or region |
| `postal-code` | ZIP or postal code |
| `country` | Country code (like `IN`) |
| `country-name` | Country name (like "India") |

The "level" names are **generic** on purpose, because countries organise addresses in different ways.

### Accounts and security

| Token | For |
| :-- | :-- |
| `username` | Username or account name |
| `current-password` | The password the visitor already has (sign in) |
| `new-password` | A **new** password (sign up, change password) |
| `one-time-code` | A code sent by SMS or an app |
| `webauthn` | Passkeys (added to a username field) |

### Payments

| Token | For |
| :-- | :-- |
| `cc-name` | Name on the card |
| `cc-number` | Card number |
| `cc-exp` | Expiry date |
| `cc-exp-month`, `cc-exp-year` | Expiry month or year, separately |
| `cc-csc` | Security code |
| `cc-type` | Card type |

### Other

| Token | For |
| :-- | :-- |
| `on` | Allow the browser to decide |
| `off` | Ask the browser **not** to remember or fill this field |
| `language` | Preferred language |
| `sex`, `bday-day`, `bday-month`, `bday-year` | Other personal details, used only when you really need them |

## Sign-In and Sign-Up Forms

Password managers depend on the right tokens, so get these right:

```html
<!-- Sign in -->
<input type="text" name="username" autocomplete="username" />
<input type="password" name="password" autocomplete="current-password" />

<!-- Sign up or change password -->
<input type="text" name="username" autocomplete="username" />
<input type="password" name="password" autocomplete="new-password" />
<input type="password" name="confirm" autocomplete="new-password" />
```

- **`current-password`** tells the manager to offer a **saved** password.
- **`new-password`** tells it to **suggest a strong new one** (and not to fill the old one).
- Use `username` (or `email`) for the account field so the manager can pair it with the password.
- Do **not** stop visitors from pasting passwords. That breaks password managers, which many people rely on for safety.

For SMS and app codes, `autocomplete="one-time-code"` lets phones offer the code from a text message with one tap.

## Shipping and Billing Sections

A checkout often asks for the same fields twice. A **section prefix** lets the browser keep them apart:

```html
<h2>Shipping address</h2>
<input name="ship_street" autocomplete="shipping address-line1" />
<input name="ship_city" autocomplete="shipping address-level2" />
<input name="ship_zip" autocomplete="shipping postal-code" />

<h2>Billing address</h2>
<input name="bill_street" autocomplete="billing address-line1" />
<input name="bill_city" autocomplete="billing address-level2" />
<input name="bill_zip" autocomplete="billing postal-code" />
```

Put `shipping` or `billing` **before** the field token. You can also use your own group name that starts with `section-`, such as `section-gift`, to separate other repeated groups, for example `autocomplete="section-gift shipping given-name"`.

## Turning It Off: `autocomplete="off"`

```html
<input type="text" name="promo" autocomplete="off" />
<form autocomplete="off"> ... </form>
```

`off` asks the browser **not to remember or suggest** values. Use it **sparingly**.

| Good reasons | Bad reasons |
| :-- | :-- |
| A **one-time** value, such as a promo code or a search that should not be saved | "I want the form to look neat" |
| Very sensitive details on a shared computer (like some banking or health pages) | Login and sign-up forms (managers should help here) |
| A field where saved values would be **wrong**, such as a CAPTCHA answer | Name, email, address, and phone fields |
| A field in an admin tool that edits someone else's record, not the visitor's own | Anything that just makes visitors retype |

Things to know:

- **Browsers may ignore `off`** for login and password fields, and for some address and card fields, because users benefit from saved details. It is a **request**, not a command.
- **Do not switch off autofill for everything.** It hurts the people who rely on it most, such as visitors with motor, memory, or cognitive differences, and everyone on a phone.
- **Inventing odd values** (like `autocomplete="nope"`) to defeat autofill is unreliable, and breaks the helpful behaviour. If you need `off`, write `off`.

## Helping Autofill Work Well

- **Use real labels** and sensible `name` attributes. Browsers use these as clues, too.
- **Use the right input type:** `email`, `tel`, `password`, `url`. They help the browser, and give the right keyboard.
- **Add `inputmode`** where useful (like `inputmode="numeric"` for postal codes and one-time codes), and `enterkeyhint` for the keyboard's action key.
- **Keep one field per piece of data,** where possible. Splitting a phone number or a card number into several small boxes often breaks autofill. If you must, give each box its own token.
- **Do not hide autofilled fields** off-screen, or make them invisible. Browsers may fill them, and the visitor never sees what was sent.
- **Let autofill finish.** Do not clear fields or reformat values while the browser is filling them.
- **Style autofilled fields sensibly.** Browsers add their own background colour. Make sure the text stays readable.

## Accessibility at a Glance

- **It is a requirement, not a bonus.** WCAG 2.1 success criterion **1.3.5, Identify Input Purpose** (level AA), asks that fields collecting information about the visitor use the right `autocomplete` value, so browsers and assistive tools can recognise what each field is for.
- **It helps real people:** those with motor difficulties (less typing), cognitive or memory differences (no need to remember or re-enter), dyslexia (fewer spelling slips), and anyone using a phone.
- **Some assistive tools can show icons** next to fields (a phone icon for `tel`), and use the token to make the form easier to understand.
- **Do not use `off`** on ordinary personal fields.
- **Keep visible labels.** Autocomplete does not replace labels.

## Security and Privacy Notes

- **Autofill is a convenience, not security.** The value your server receives can be anything, so validate on the server.
- **Autofill can fill fields the visitor cannot see.** In an old attack, hidden fields in a page were filled with the visitor's saved details and sent on. Modern browsers fill a field only after the visitor chooses a suggestion, but still: **do not add hidden fields that collect personal data** the visitor did not agree to share.
- **Password managers are good for security.** They create strong, unique passwords and fill only on the right website. Do not fight them with `off` or blocked paste.
- **Be careful on shared computers.** For pages where the next person on the same device must not see saved values (a library or a kiosk), `off` can be right, and you should also **sign visitors out** after a short idle time.
- **Never store full card numbers or passwords yourself** in the form, in the page, or in the browser. Use a trusted payment provider.
- **Pre-filling a form** from your server (for example, an account page) should be done carefully: show only the visitor's own data, and escape it properly.

## Global Audience Notes

- **Addresses work differently everywhere.** The tokens `address-level1` and `address-level2` are generic for this reason. Do not assume "state" and "zip code" labels. Use labels that fit the visitor's country.
- **Name order differs.** Many cultures put the family name first, and some people have one name only. A single `name` field with `autocomplete="name"` is often the kindest choice.
- **Phone formats differ.** `tel` gives the full international form, and `tel-national` leaves out the country code. Think about which your system expects.
- **Browser language matters.** The browser matches fields to saved data in the visitor's own language and region.
- **Right-to-left pages** work with autofill, but check that the suggestion list and your field layout still look right.
- **Do not guess from the IP address** and prefill a country for them without letting them change it.

## Common Mistakes to Avoid

1. **Using `autocomplete="off"` on everything,** so visitors retype the same details.
2. **Using `current-password` on a sign-up form,** or `new-password` on a sign-in form.
3. **Blocking paste** into password fields.
4. **Splitting phone or card numbers** into many boxes that autofill cannot fill.
5. **Inventing values** like `autocomplete="nope"` to fight autofill.
6. **Forgetting shipping and billing prefixes,** so the browser mixes the two addresses.
7. **Misspelled tokens** (`autocomplete="e-mail"`), which the browser ignores.
8. **Leaving out `username`** on sign-in and sign-up forms, so password managers cannot pair the account.
9. **Using `type="number"`** for postal codes or cards, which removes leading zeros and spoils autofill.
10. **Hidden fields** that collect personal data without the visitor knowing.
11. **Assuming every browser suggests the same thing.** Test, but do not rely on seeing suggestions.
12. **Treating `autocomplete` as validation or security.**

<summary>1. What does the `autocomplete` attribute do?</summary>

It tells the browser what kind of information a field wants (name, email, address, password, and so on), so the browser or password manager can offer saved values. It does not validate or change what is sent.

<details>
<summary>2. What is the difference between `current-password` and `new-password`?</summary>

`current-password` asks the password manager to offer the visitor's saved password (sign in). `new-password` asks it to suggest a new, strong password and not to fill the old one (sign up, change password).

</details>

<details>
<summary>3. How do you keep shipping and billing addresses apart?</summary>

Put a section prefix before the token: `autocomplete="shipping postal-code"` and `autocomplete="billing postal-code"`.

</details>

<details>
<summary>4. When is `autocomplete="off"` appropriate?</summary>

For one-time values (such as a promo code), for fields where saved values would be wrong, and for very sensitive pages on shared computers. It is not appropriate for ordinary name, email, address, and login fields. Browsers may ignore it anyway.

</details>

<details>
<summary>5. Why does `autocomplete` matter for accessibility?</summary>

It is required by WCAG 1.3.5 (Identify Input Purpose). It saves typing and memory effort for people with motor and cognitive differences, and lets assistive tools recognise what each field is for.

</details>

<details>
<summary>6. Is `autocomplete` a security feature?</summary>

No. It is a convenience. The server must still validate every value. Password managers it works with are good for security, so do not block them.

</details>

## Key Takeaways

- `autocomplete` tells browsers and password managers what a field is for, using tokens like `name`, `email`, `tel`, `postal-code`, and `cc-number`.
- Use `username`, `current-password`, and `new-password` correctly, and `one-time-code` for verification codes.
- Add `shipping` or `billing` before a token to separate two address groups.
- Use `autocomplete="off"` rarely. It is a request, and browsers may ignore it.
- Good autofill is an accessibility requirement (WCAG 1.3.5), and a big help on phones.
- Keep labels, sensible names, and the right input types, and do not split data into tiny boxes or block paste.
- It is a convenience, not security. **Validate on the server.**
