import {useState, useEffect, useRef} from 'react';

export const slotShadowHtml = '<style>.card { border: 1px solid #888; border-radius: 8px; padding: 0.75rem; } header { font-weight: 700; } .body { margin: 0.4rem 0; } footer { font-size: 0.85rem; opacity: 0.85; }</style><div class="card"><header><slot name="title">Untitled (fallback)</slot></header><div class="body"><slot>No content yet (fallback)</slot></div><footer><slot name="footer">No footer (fallback)</slot></footer></div>';

export function reportSlots(host) {
  const root = host.shadowRoot;
  if (!root) return null;
  const defs = [["title", 'slot[name="title"]'], ["default", "slot:not([name])"], ["footer", 'slot[name="footer"]']];
  const rows = defs.map(function (d) {
    const s = root.querySelector(d[1]);
    const count = s ? s.assignedNodes().length : 0;
    return {slot: d[0], count: count};
  });
  const unassigned = Array.from(host.children).filter(function (el) { return el.assignedSlot === null; }).map(function (el) {
    return "<" + el.tagName.toLowerCase() + ' slot="' + el.getAttribute("slot") + '">';
  });
  return {rows: rows, unassigned: unassigned};
}

# The slot Element

A `template` gives you a blueprint you can copy. But what if the people using your blueprint want to **put their own content inside it**: their own title, their own text, their own button? Filling in every field from JavaScript gets clumsy. The **`slot` element** solves this in a more HTML-like way. A component leaves **openings**, and the page author drops content into them with plain markup.

## Where Slots Work

A `slot` only does something **inside a shadow root.** A shadow root is a private, separate bit of DOM attached to an element, which lets a component keep its own markup and styles apart from the page. You will build one properly in [Web Components in HTML](./web-components-html). For now, you only need the vocabulary:

| Word | Meaning |
| :-- | :-- |
| **Host** | The element the shadow root is attached to, such as `recipe-card` |
| **Shadow root / shadow DOM** | The component's private markup, where its `slot` elements live |
| **Light DOM** | The ordinary children the page author wrote inside the host |
| **Slotted content** | Light DOM nodes that the browser assigned to a slot |
| **Flat tree** | What the browser actually draws: the shadow DOM, with slotted content placed in its slots |

A `slot` written in an ordinary page, with no shadow root around it, does nothing special.

The key idea: **slotted content stays in the light DOM.** It is still part of the page. You can find it with `document.querySelector`, style it from the page's CSS, and it is part of any form it sits in. The browser only **draws** it in the slot's position.

## Default and Named Slots

- A `slot` **without a name** is the **default slot.** It receives every direct child of the host that has no `slot` attribute, including plain text.
- A `slot` **with a `name`** receives the direct children whose `slot` attribute matches that name.

```html
<!-- Inside the component's shadow root -->
<slot name="title"></slot>   <!-- gets slot="title" -->
<slot></slot>                <!-- gets everything else -->
<slot name="footer"></slot>  <!-- gets slot="footer" -->
```

Rules that explain most surprises:

1. **Only direct children of the host are assigned.** A `slot` attribute on a deeper element is ignored. The whole direct child goes to a slot, with its descendants.
2. **Several elements can share one slot.** They appear in the order they were written.
3. **An element with a `slot` attribute that matches no slot is not drawn.** It stays in the page's DOM, but nowhere visible.
4. **Text counts.** Loose text directly inside the host goes to the default slot.

Open the **Slot Lab** and try these. Tick the "second paragraph" box, then the "subtitle" box, and read the table. Then try the **Which Slot?** tab.

## Fallback Content

Whatever you place **inside** a `slot` is shown only when nothing is assigned to it:

```html
<slot name="title">Untitled</slot>
```

If the page author provides no title, the card shows "Untitled". Good fallbacks make a component work with little or no content. Untick the title in the lab, and you see it.

Keep fallbacks short and neutral, because they appear in whatever language the page uses. See the global notes below.

## Styling Slotted Content

Because slotted nodes live in the light DOM, **the page's CSS applies to them** as usual. The component can also style them from inside, using the `::slotted()` pseudo-element:

```css
/* In the component's shadow styles */
::slotted(h3) { margin: 0; }
::slotted(*) { max-width: 100%; }
```

Know its limits:

- `::slotted()` reaches only the **top-level** slotted elements, not their children.
- If the page's own CSS and a `::slotted()` rule disagree, **the page's CSS wins.** That lets page authors always override a component.
- For anything deeper, a component can expose **CSS custom properties** (such as `--card-border`) or **parts** (the `part` attribute), which you will meet in the next lesson.

Check "Page CSS: colour the title red" in the lab. The page reaches into the slotted title with no special tools.

## Watching and Reading Slots

Slots have a small API:

```js
const slot = root.querySelector('slot[name="title"]');

slot.assignedNodes();                    // nodes assigned, including text
slot.assignedElements();                 // elements only
slot.assignedNodes({ flatten: true });   // also follows slots nested in slots
someElement.assignedSlot;                // which slot an element ended up in, or null

slot.addEventListener("slotchange", () => {
  console.log("Title now has", slot.assignedElements().length, "element(s)");
});
```

- **`slotchange`** fires when the **assignment** changes: nodes added, removed, or given a different `slot` name. It does not fire when the text inside a slotted element changes.
- **`assignedSlot`** is how the lab tells which elements ended up nowhere. It returns `null` for those.

## Accessibility

Slots help accessibility when used well, and cause trouble when used carelessly.

- **Let the page author choose the heading level.** A component that hard-codes an `h2` inside its shadow DOM can break the page's outline. Slotting the heading, as in `<h3 slot="title">`, lets each page use the right level.
- **Slotted content keeps its meaning.** A real heading, link, or button in the light DOM is announced as such.
- **IDs do not cross the shadow boundary.** Attributes that point at an `id`, such as `for` on a `label` and `aria-labelledby`, work only within the same tree. A label in the shadow DOM cannot point at an input in the light DOM, and the reverse. Keep related elements together on one side, or build the component to expose what it needs.
- **Form fields are best slotted.** An `input` in the light DOM belongs to the page's form and submits normally. An `input` hidden inside a shadow root does not take part in the surrounding form unless the component is built specially for it.
- **Check the reading order.** The flat tree decides what is read and tabbed through. Test with the keyboard.

## Before and Without the Component

Because slotted content is ordinary light DOM, a good component **degrades gracefully**:

- Until JavaScript defines the component, or in a browser without support, the children simply show as normal markup. A heading, a paragraph, and a note are still readable.
- You can style the not-yet-ready state with `:not(:defined)` in your page CSS.

So write the light DOM as **real, meaningful HTML first**, such as headings, paragraphs, and links, and treat the component as an upgrade.

## Slots or Templates and Data Fields?

| | Slots | A template filled from JavaScript |
| :-- | :-- | :-- |
| Content written as | Plain HTML, by the page author | Data, filled by your script |
| Works without JavaScript | Content is still there | Nothing appears |
| Best for | Reusable layouts that authors fill in | Lists built from data, such as rows from a server |
| Needs a shadow root | Yes | No |

They also work well together: a component clones a template into its shadow root, and that template contains the slots.

## Best Practices

1. **Name slots after their purpose,** such as `title` and `footer`.
2. **Provide short, neutral fallback content.**
3. **Slot headings,** so page authors control the outline.
4. **Slot form controls,** so they stay in the page's form.
5. **Write the light DOM as real, meaningful HTML.**
6. **Keep the page's CSS able to override the component.**
7. **Use `slotchange`** when your component must react to changes.
8. **Document your slots,** so authors know the names.
9. **Test with missing content, and with extra content.**
10. **Test with the keyboard and a screen reader.**

## Quick Checklist

- [ ] Each slot has a clear name, or is the one default slot
- [ ] Each slot has sensible fallback content, or is meant to be empty
- [ ] Headings and form controls are slotted, not hard-coded
- [ ] The light DOM makes sense without the component
- [ ] Unmatched `slot` names are not relied on
- [ ] Ids and ARIA references stay within one tree
- [ ] The component works with the keyboard and a screen reader
- [ ] Slot names are documented

## Security and Privacy Notes

- **Shadow DOM is not a security boundary.** An open shadow root can be read by any script on the page, and scripts can reach inside it. Never keep secrets in a component's markup.
- **Slotted content is page content.** It is subject to the page's Content Security Policy, and anything inserted there is as dangerous as any other markup. If visitor text is shown in a slot, set it with `textContent`. See [XSS Basics](/tutorials/html/security/xss-basics).
- **Strip `slot` attributes from untrusted HTML.** If you accept visitor-written HTML (after sanitising), a `slot` attribute on it could place content into a part of your component, such as a footer or a banner, that you meant to be trusted. This is a layout-spoofing trick, so remove the attribute when you sanitise.
- **Do not build the shadow template from visitor text.** Use a fixed string, or a `template`, and fill values with `textContent`.
- **Slots can reveal content.** Anything in the light DOM is in the page source, even if the component hides it.

## Global Audience Notes

- **Writing direction is inherited.** Slotted content follows the page's `dir` and `lang`, and a card or other component should use logical properties such as `padding-inline-start`.
- **Fallback text is visible to everyone,** so it must be translatable. Pass it through your translation system, or use an `aria-label` and icons that work in any language.
- **Long and short text vary** across languages. Do not set a fixed height on slotted regions.
- **Let authors supply content in their own language.** Slots are good for this, because the component does not impose any words.
- **Headings and labels in the page's language** help screen readers choose the right voice.

## Common Mistakes to Avoid

1. **Expecting a slot to work without a shadow root.**
2. **Putting the `slot` attribute on a deeper element** than a direct child.
3. **Misspelling a slot name,** so the content vanishes.
4. **Hard-coding headings** inside the component.
5. **Expecting `label for` or `aria-labelledby`** to cross the shadow boundary.
6. **Hiding form controls** inside shadow DOM and expecting them to submit.
7. **Forgetting fallback content,** and showing empty boxes.
8. **Trying to style deep slotted content** with `::slotted()`.
9. **Believing shadow DOM keeps secrets.**
10. **Leaving `slot` attributes in sanitised visitor HTML.**

## Key Takeaways

- **A slot is an opening in a component** where the page author's content appears.
- **Default slot for the rest, named slots for the parts.** Only direct children are assigned.
- **Fallback content** shows when nothing is assigned.
- **Slotted content stays in the light DOM,** so the page can style and query it.
- **IDs and ARIA references do not cross the shadow boundary.** Slot headings and form controls.
- **Shadow DOM is not security.** Use `textContent`, and strip `slot` attributes from untrusted HTML.
- **Write meaningful light DOM first.** The component is an upgrade.
