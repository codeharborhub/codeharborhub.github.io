export const statusText = {
  widely: "It works in all the major browsers, and has for a long time.",
  newly: "It works in the latest versions of the major browsers, but older versions are still in use.",
  limited: "Only some browsers support it."

export const audienceText = {

  mixed: "Your visitors include older or shared devices.",
  old: "Some visitors must use very old browsers, such as a kiosk or an office computer that is not updated."
};

export function decideReadiness(status, degrades, audience) {
  let verdict;
  if (status === "widely") {
    if (audience === "old") verdict = degrades ? "Use it as an enhancement" : "Use it only with a fallback";
    else verdict = "Use it";
  } else if (status === "newly") {
    if (audience === "current") verdict = degrades ? "Use it as an enhancement" : "Use it only with a fallback";
    else verdict = degrades ? "Use it as an enhancement" : "Wait";
  } else {
    if (degrades && audience !== "old") verdict = "Use it as an enhancement";
    else verdict = "Wait";
  }
  const advice = {
    "Use it": "Write it normally, and keep testing in more than one browser.",
    "Use it as an enhancement": "Build a page that works without it, and let the feature improve things where it is available.",
    "Use it only with a fallback": "The page needs the feature to work, so provide a fallback, such as a different element, a polyfill, or a simple alternative.",
    "Wait": "The risk is higher than the benefit. Revisit it when support has spread, or choose a widely supported alternative."
  };
  return {verdict: verdict, advice: advice[verdict], reasons: [statusText[status], audienceText[audience], degrades ? "If the feature is missing, the page still works." : "If the feature is missing, part of the page stops working."]};
}

# Modern HTML Features

HTML keeps growing. Alongside big features such as `dialog` and `popover`, which have lessons of their own, there is a set of **small, practical additions** that make forms friendlier, pages faster, and content easier to use for a global audience. This lesson is a guided tour of them, followed by a method for judging whether any new feature is ready for **your** site.

## What You Will Learn

- The `search` element, a landmark for search forms
- `inputmode` and `enterkeyhint`, which shape the phone keyboard
- `fetchpriority` and `decoding`, hints for images and resources
- `hidden="until-found"`, `translate`, and `spellcheck`
- Module scripts and import maps
- A simple way to decide whether a feature is ready

## The Big Idea

Most modern features are **hints and improvements**, not new building blocks. If you add them to a solid page, browsers that understand them give visitors a better experience, and browsers that do not simply ignore them. That is the safest way to adopt new HTML.

## The search Element

The `search` element marks the part of a page that holds search or filtering controls. It gives assistive technology a **search landmark**, so screen reader users can jump straight to it.

```html
<search>
  <form action="/search" method="get">
    <label for="q">Search recipes</label>
    <input id="q" type="search" name="q">
    <button type="submit">Search</button>
  </form>
</search>
```

Before it existed, you wrote `<form role="search">`. That still works, and is a sensible choice if you must support older browsers, because they treat an unknown element such as `search` as a plain wrapper with no landmark meaning. A `search` element is not a form, so keep a `form` inside it.

Use it for site search, and for filter panels on listing pages. Do not use it for anything that is not search.

## inputmode and enterkeyhint

On a phone, the keyboard that appears depends on the field. Two attributes let you fine-tune it:

```html
<input type="text" inputmode="numeric" pattern="[0-9]{6}" autocomplete="one-time-code">
<input type="search" enterkeyhint="search">
```

- **`inputmode`** suggests which keyboard to show. Common values are `numeric`, `decimal`, `tel`, `email`, `url`, and `search`.
- **`enterkeyhint`** changes the label or icon of the enter key. Values include `enter`, `done`, `go`, `next`, `previous`, `search`, and `send`.

Neither one validates anything, and both are only **hints**. A browser or keyboard may ignore them.

### A good reason to use inputmode

`type="number"` looks right for codes and card numbers, but it has problems: it adds spinner arrows, scrolling the mouse wheel can change the value, and it drops leading zeros. For a PIN or a postal code, use `type="text"` with `inputmode="numeric"` and a `pattern`, and validate on the server, as covered in [Secure Forms](/html/security/secure-forms).

For amounts with decimals, `inputmode="decimal"` shows a keyboard with a decimal key. Remember that some regions use a comma as the decimal mark, so accept both on the server.

## fetchpriority and decoding

Two attributes help the browser decide **what to load first** and **how to prepare an image**.

```html
<img src="/img/hero.jpg" alt="..." width="1200" height="600"
     fetchpriority="high" decoding="async">
```

- **`fetchpriority`** accepts `high`, `low`, or `auto`. It nudges the browser's choice of when to download a resource. It works on `img`, `link`, and `script`. It is a hint, not a command.
- **`decoding="async"`** lets the browser decode an image away from the main flow of work, so the page stays responsive. The default is `auto`.

The best use of `fetchpriority="high"` is on the single image that is your Largest Contentful Paint element. Do not put it on many images, because then none of them stands out. See [Core Web Vitals](/html/performance/core-web-vitals) and [Critical Resources](/html/performance/critical-resources).

## hidden="until-found"

The ordinary `hidden` attribute removes content from the page and from find-in-page. A newer value changes that:

```html
<div hidden="until-found">
  <p>Shipping takes two working days.</p>
</div>
```

With `until-found`, the content stays hidden **until the visitor's find-in-page search or a link to a fragment matches it**. Then the browser reveals it. A `beforematch` event fires so your script can react.

The catch is support: where it is missing, the content stays hidden and cannot be found. So use it only for content that is **not essential**, or consider `details` and `summary`, which have long been supported. See [Details and Summary](./details-summary).

## translate, spellcheck, and autocapitalize

These global attributes are small, but they matter for people around the world:

```html
<p>Our shop is called <span translate="no">DoughNation</span>.</p>
<code translate="no">npm install</code>
<input type="text" name="username" spellcheck="false" autocapitalize="none" autocomplete="username">
```

- **`translate="no"`** tells page translators to leave the text alone. Use it for brand names, code, and product codes, so a translator does not turn them into nonsense.
- **`spellcheck="false"`** stops red underlines on usernames, codes, and other text that is not ordinary prose.
- **`autocapitalize`** controls automatic capital letters on mobile keyboards. `none` is helpful for usernames and email addresses.

They cost almost nothing to add, and they help most on pages that visitors translate or open on many kinds of devices.

## Module Scripts and Import Maps

Modern JavaScript is written in **modules**, which are files that import and export values.

```html
<script type="module" src="/js/app.js"></script>
```

What makes module scripts different from classic scripts:

- They are **deferred** by default, so they run after the page is parsed, like `defer` in [Script Loading](/html/performance/script-loading).
- They run in **strict mode**, and keep their variables to themselves.
- A browser loads each module once, even when several files import it.

An **import map** lets you use short names instead of long paths:

```html
<script type="importmap">
  { "imports": { "confetti": "/js/vendor/confetti.js" } }
</script>
<script type="module">
  import { launch } from "confetti";
  launch();
</script>
```

The import map must come **before** the module scripts that use it.

:::warning
If your site has a Content Security Policy, an **inline** import map or inline module is blocked unless it carries a nonce or matches a hash, exactly like any inline script. See [Content Security Policy](/html/security/content-security-policy). Scripts from other origins also need the right `crossorigin` handling, so read the details before you add them.
:::

## Other Small Elements Worth Knowing

These are not new, but they are underused and worth a second look:

| Element | What it is for |
| :-- | :-- |
| `time` | A date or time that machines can read, using `datetime` |
| `progress` and `meter` | A task's progress, and a measurement within a known range |
| `output` | The result of a calculation or an action |
| `mark` | Text highlighted because it is relevant right now, such as a search match |
| `data` | A human-readable value with a machine-readable `value` |

## Coming Soon, or Only in Some Browsers

New ideas often appear first in a single browser. When only one browser supports a feature, treat it as **experimental**:

- Do not build important parts of a page on it.
- Use it as a small enhancement, if it degrades gracefully.
- Watch its support and Baseline label, and come back later.

The **Readiness Judge** tab turns this into a simple decision tool. Try the combinations, and see how the advice changes.

## A Quick Way to Learn Any New Feature

1. **Read the top of its MDN page.** What does it do, in one sentence?
2. **Open the compatibility table,** and find the Baseline label.
3. **Build a tiny test page** with only that feature.
4. **Test with the keyboard,** and in a second browser, and on a phone if you can.
5. **Decide the fallback,** using the Readiness Judge.
6. **Add a short comment** in your code with the feature name and the date you checked.
7. **Re-check from time to time,** as support grows.

## Checking Your Setup

1. On MDN, open each feature you use, and check its **Baseline** label and compatibility table.
2. Use DevTools' **device mode** to approximate a phone, and a real phone to see the real keyboard.
3. Turn the feature off in your head: if it were missing, would the page still work?
4. Open the **Console** for warnings about unknown attributes or blocked scripts.
5. Test with a screen reader or at least the keyboard, for `search`, `hidden`, and any form changes.

## Best Practices

1. **Use new features as enhancements** on top of a working page.
2. **Check support** on MDN or Baseline before relying on a feature.
3. **Use `inputmode` for codes,** instead of `type="number"`.
4. **Put `fetchpriority="high"` on one image,** the likely LCP element.
5. **Mark brand names and code with `translate="no"`.**
6. **Prefer `details`** over `hidden="until-found"` for important content.
7. **Keep `form` inside `search`,** and add `role="search"` to forms for older browsers if needed.
8. **Order import maps first,** and allow them in your CSP.
9. **Comment the date** you checked support.
10. **Re-check old decisions** when browsers update.

## Security and Privacy Notes

- **`inputmode` and `pattern` are not validation.** A visitor can send anything. The server must check every value. See [Secure Forms](/html/security/secure-forms).
- **Module scripts follow the same rules as other scripts.** Only load them from places you trust, use `https`, and keep your CSP in mind.
- **`hidden` hides, it does not protect.** Anything in the HTML is sent to every visitor and is readable in the page source. Never hide private information that way.
- **`translate` and page translators:** a translator sends text to a translation service. Mark text such as personal data and codes with `translate="no"`, and do not paste private pages into online translators.

## Global Audience Notes

- **`translate="no"`** protects brand names and technical terms when visitors use their browser's translation, which is common worldwide.
- **Keyboards and input methods differ.** Many people type with an input method editor for languages such as Chinese, Japanese, and Korean. Avoid code that breaks as people compose characters, and use `inputmode` only where it truly helps.
- **Number formats differ.** Decimal marks, digit shapes, and grouping vary, so accept more than you display.
- **Older and low-cost phones** are common. A feature that fails quietly is better than one that breaks the page.

## Common Mistakes to Avoid

1. **Adopting a feature without checking support.**
2. **Building critical content** on something only one browser supports.
3. **Using `type="number"`** for codes, instead of `inputmode`.
4. **Giving `fetchpriority="high"` to many images.**
5. **Hiding essential content** with `hidden="until-found"`.
6. **Placing the import map after** the module that needs it.
7. **Forgetting the CSP** for inline import maps and modules.
8. **Using `search`** for anything that is not search.
9. **Treating hints** as guarantees.
10. **Never re-checking** after browsers change.

## Key Takeaways

- **Most modern features are hints and improvements.** Add them to a solid base.
- **`search`, `inputmode`, `enterkeyhint`, `fetchpriority`, `decoding`, `translate`, and `spellcheck`** are small changes with real benefits.
- **`hidden="until-found"` needs care,** because missing support hides content.
- **Modules and import maps** are the modern way to organise scripts, and still obey your CSP.
- **Check support, decide the fallback, and test.**
- **Hints are not validation or security.** The server still checks everything.
