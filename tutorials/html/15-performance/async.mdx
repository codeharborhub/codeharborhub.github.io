import {useState} from 'react';

export function mulberry32(seed) {
  let a = seed >>> 0;
  return function () {
    a = (a + 0x6D2B79F5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export function raceLoads(mode, jitter, seed, count) {
  const rand = mulberry32(seed);
  const loads = [];
  for (let i = 0; i < count; i++) {
    const libMs = Math.max(20, 200 + (rand() * 2 - 1) * jitter);
    const appMs = Math.max(20, 260 + (rand() * 2 - 1) * jitter);
    let order;
    if (mode === "async") order = appMs < libMs ? ["app.js", "lib.js"] : ["lib.js", "app.js"];
    else order = ["lib.js", "app.js"];
    loads.push({n: i + 1, lib: Math.round(libMs), app: Math.round(appMs), order: order, ok: order[0] === "lib.js"});
  }
  return {loads: loads, failures: loads.filter(function (l) { return !l.ok; }).length};
}

Where `defer` says "run me when the page is ready", `async` says "run me the moment I arrive." The script downloads in the background without stopping the page, and the instant it has downloaded, the browser runs it, even if it has to pause reading the HTML to do so.

That makes `async` perfect for scripts that stand alone, and a source of confusing bugs for scripts that do not. This lesson explains both sides. The wider picture is in [Script Loading](./script-loading), and its companion is [Defer](./defer).

## The Rules of async

1. **It downloads in parallel,** just like `defer`.
2. **It runs as soon as it has downloaded.** That may be before the page is fully read, or after.
3. **If it arrives while the page is being read, the parser pauses** until the script has run.
4. **It has no order.** Whichever script arrives first runs first, whatever the order in the HTML.
5. **`DOMContentLoaded` does not wait for it.** The event can fire before or after an async script runs.
6. **It only works on external scripts.** Inline classic scripts ignore it. A module script with `async` runs as soon as it and its imports are ready, instead of waiting until the end.

## async vs defer

| | `defer` | `async` |
| :-- | :-- | :-- |
| Runs | After the page is read | As soon as it arrives |
| Order kept | Yes | No |
| Can pause page reading | No | Yes, if it arrives early |
| Does `DOMContentLoaded` wait for it? | Yes | No |
| Can it use the whole page? | Yes | Not guaranteed |
| Best for | Your own scripts, and scripts that depend on each other | Independent scripts, such as analytics |

:::tip
A simple rule: if it depends on nothing and nothing depends on it, use `async`. For everything else, use `defer`.
:::

## The Race Condition

Imagine two scripts, where `app.js` needs `lib.js`. On your fast office connection `lib.js` always arrives first, the page always works, and you ship it. Then a visitor on a different network gets `app.js` first. It runs, finds no library, and fails.

This is a **race condition**: the result depends on which download wins. It is the worst kind of bug, because it appears only sometimes, and rarely for the developer. The Race Lab shows it. If you ever see an error like "X is not defined" that comes and goes, check for `async` on scripts that depend on each other.

## The DOMContentLoaded Trap

Many scripts start their work like this:

```js
document.addEventListener("DOMContentLoaded", function () {
  startApp();
});
```

That is fine for a plain or deferred script, because the event has not fired yet when they run. But an `async` script may arrive **after** the event has already fired. Then the listener waits for something that has already happened, and `startApp` never runs.

The fix is to check the state first:

```js
function ready(fn) {
  if (document.readyState === "loading") {
    document.addEventListener("DOMContentLoaded", fn);
  } else {
    fn();
  }
}

ready(function () {
  startApp();
});
```

If the page is still being read, wait. If it is already read, go straight ahead. Code written this way works in every loading mode.

## Calling a Script Before It Arrives

Sometimes your page wants to call a function from an async script, but it may not have arrived yet. A common pattern is a small **queue**: you create a stand-in function that stores the calls, and the real script reads the queue when it arrives.

```html
<script>
  window.track = window.track || function () {
    (window.track.q = window.track.q || []).push(arguments);
  };
  track("page_view");
</script>
<script src="https://stats.example.com/tracker.js" async></script>
```

This only works if the provider's script is built to read the queue, as many analytics tools are. Follow the instructions of the service you use, rather than inventing the pattern yourself.

## async Can Still Slow the Page

Async does not block the **download**, but it can block the **parser** when it runs. If a big async script arrives while the page is still being read, the page pauses to run it. A heavy third-party tag arriving early can delay your content.

- Keep async scripts small, or load them later (after the page has loaded, or on interaction).
- Remember that running a script still takes time on the main thread, which can hurt responsiveness.
- Check the Performance panel to see whether an async script runs in the middle of page reading.

## Scripts Added by JavaScript

A script you add from JavaScript with `document.createElement("script")` behaves like `async` by default. If you add several that depend on each other, tell the browser to keep their order:

```js
["/js/lib.js", "/js/app.js"].forEach(function (src) {
  const s = document.createElement("script");
  s.src = src;
  s.async = false;
  document.head.appendChild(s);
});
```

With `async = false`, scripts added this way download in parallel but run in the order they were added.

## Checking in DevTools

1. Open DevTools, then **Network**, filter by **JS**, and reload several times. Does the order of the async scripts change?
2. In the **Performance** panel, record a load, and look for where an async script runs. Does it interrupt the page being read?
3. Throttle the network, and reload. Do any "is not defined" errors appear that did not before?
4. Use the **Console** to check for errors from scripts running in the wrong order.
5. Try blocking one async script (DevTools can block a request). Does the page still work without it?

## Best Practices

1. **Use `async` only for independent scripts.**
2. **Never use it on scripts that depend on each other.** Use `defer`.
3. **Write start-up code with a `readyState` check,** not only a `DOMContentLoaded` listener.
4. **Keep async scripts small,** or load them late.
5. **Use a queue** where the provider supports one, to call a script before it arrives.
6. **Make sure the page works** if an async script never loads.
7. **Reserve space** for anything an async script adds, so the layout does not jump.
8. **Test with throttling and repeated loads,** to catch race conditions.

## Quick Checklist

- [ ] Every `async` script is independent
- [ ] Dependent scripts use `defer`
- [ ] Start-up code checks `document.readyState`
- [ ] The page works if an async script is blocked or fails
- [ ] Async scripts are small, or load after the page
- [ ] Space is reserved for anything they add (ads, widgets)
- [ ] Several throttled reloads show no "is not defined" errors

## Security and Privacy Notes

- **An async script has the full power of your page,** and it runs whenever it arrives, even while the page is half-read. Load scripts only from sources you trust.
- **Most async scripts are third-party.** Analytics, ads, and widgets can collect data and set cookies as soon as they run. If you need consent first, do not load them until it is given. This is not legal advice, so check the rules that apply to you.
- **Use integrity hashes for fixed files.** For a script that never changes, add `integrity` and `crossorigin="anonymous"`, so the browser rejects an altered file.
- **Use a content security policy** to limit which hosts may supply scripts. It can also block inline code, so test it carefully.
- **Do not make your page depend on an async script for security.** For example, do not rely on one to hide or protect content, because it may never load, or may run late.
- **Never build a script URL from untrusted input.**

## Global Audience Notes

- **A blocked or slow script should not hurt your page.** In some regions, networks, or browsers with blockers, third-party scripts never arrive. That is exactly where `async` is kind: the page carries on without them. Make sure it really does.
- **Timing differs by network,** which is why async bugs show up for some visitors and not others. Test on slow connections as well as your own.
- **Heavy tags cost more on modest phones,** because running them uses the same limited processor. Keep the number of async third-party scripts small.
- **Layout shifts hurt slow networks most.** An ad or widget that pops in late and pushes content down is worse when it arrives seconds later. Reserve space for it.

## Common Mistakes to Avoid

1. **Using `async` on scripts that depend on each other.**
2. **Relying on a `DOMContentLoaded` listener** inside an async script.
3. **Assuming the page is fully read** when an async script runs.
4. **Assuming the order in the HTML** is the order of running.
5. **Loading a heavy third-party tag early,** so it pauses the page.
6. **Using `async` on an inline script,** where it does nothing.
7. **Setting both `async` and `defer`** on the same tag.
8. **No reserved space** for what an async script adds.
9. **Testing once on a fast connection,** and calling it done.
10. **Making the page depend on a script** that may never load.

## Key Takeaways

- **`async` runs as soon as the script arrives,** with no order guaranteed.
- **Use it for independent scripts,** and `defer` for everything that depends on something.
- **Race conditions are flaky.** Test with throttling and repeated loads.
- **Do not rely on `DOMContentLoaded` inside an async script.** Check `readyState`.
- **An async script can still pause the page** when it runs, so keep it small or load it late.
- **Design for a script that never arrives,** and reserve space for what it adds.
- **Mind privacy and trust:** wait for consent where needed, and use integrity hashes for fixed files.
