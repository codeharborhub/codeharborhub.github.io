import {useState} from 'react';

export function prefetchValue(chance, sizeKb, mbps) {
  const seconds = (sizeKb * 8) / (mbps * 1000);
  const wastedKb = Math.round((1 - chance) * sizeKb);
  let verdict = "Probably skip it.";
  if (chance >= 0.5 && sizeKb <= 1000) verdict = "Usually a good bet.";
  else if (chance >= 0.3 && sizeKb <= 300) verdict = "Maybe, if the connection is not metered.";
  return {seconds: Math.round(seconds * 10) / 10, wastedKb: wastedKb, verdict: verdict};
}

# Prefetch in HTML

Preload is for files this page needs right now. **Prefetch** looks forward. It is a way to say, "the visitor will probably go here next, so when you have a quiet moment, fetch it for me."

Done well, the next page feels instant, because much of it is already waiting in the browser's cache. Done carelessly, prefetch spends your visitor's data on pages they never open. This lesson helps you aim well.

## What You Will Learn

- What `rel="prefetch"` does, and how it differs from preload
- How to decide which pages and files are worth prefetching
- What a prefetch can and cannot do for the next page
- How to prefetch on hover or when the browser is idle, and respect data saving
- What must never be prefetched
- How to check whether prefetching helped

## The Big Idea

A prefetch is a `link` element that names a file or page the visitor may need next.

## What Prefetch Does

1. **It fetches at low priority.** The browser waits until it is not busy with files the current page needs.
2. **It stores the result.** The file goes into the browser's cache, to be used if the visitor asks for it later.
3. **It keeps going after the visitor leaves.** Unlike most downloads, a prefetch can carry on while the next page is loading, which is the whole point.
4. **It does not run or show anything.** A prefetched script does not run, and a prefetched page does not appear. It is simply ready, if needed.
5. **It is a hint.** The browser can skip it, for instance on a slow connection or with data saving on, and support differs between browsers, so check [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel/prefetch) before relying on it.

## Prefetch vs Preload

They look alike, but they answer different questions.

| Question | Preload | Prefetch |
| :-- | :-- | :-- |
| Which page is it for? | This page, now | The next page, maybe |
| Priority | High | Low |
| Is `as` needed? | Yes | Optional, but helpful |
| What if it is wasted? | Competes with this page | Wastes data and bandwidth |
| Typical use | Fonts, hero images, late-found files | The next page, or the files it needs |

A simple rule: if the **current** page needs it, use preload (or better, put it in the HTML). If only the **next** page might need it, use prefetch. Using prefetch for something the current page needs is a mistake, because the low priority means it arrives late.

## What Gets Prefetched for a Page

If you prefetch a page address, the browser usually fetches just that one HTML file. The files that page uses (its stylesheets, scripts, and images) are not automatically included. So for a smoother jump, you may prefetch the key files as well:

```html
<link rel="prefetch" href="/order">
<link rel="prefetch" href="/js/order.js" as="script">
<link rel="prefetch" href="/css/order.css" as="style">
```

How much of this helps depends on your caching headers. A file the server marks as cacheable will be kept and reused. Behaviour for files that are not cacheable differs between browsers, so test in the ones your visitors use.

## Choosing What to Prefetch

Prefetch only when all of these are true:

- **It is likely.** A good rule of thumb is that around half of visitors, or more, go there next.
- **It is small.** A big page or file is a big bet.
- **It is public and safe.** A plain GET request that changes nothing and holds nothing private.
- **It is useful in the cache.** The page or file can actually be reused when the visitor arrives.

## Prefetching on Hover or When Idle

You do not have to prefetch everything on page load. A common, careful approach is to prefetch when the visitor shows interest, for example when they hover a link. This keeps the bet small, because they are clearly considering it.

```js
const done = new Set();

function prefetch(url) {
  if (done.has(url)) return;
  const c = navigator.connection;
  if (c && (c.saveData || /2g/.test(c.effectiveType))) return;
  done.add(url);
  const link = document.createElement("link");
  link.rel = "prefetch";
  link.href = url;
  document.head.appendChild(link);
}

document.querySelectorAll("a[data-prefetch]").forEach(function (a) {
  if (a.origin !== location.origin) return;
  a.addEventListener("mouseenter", function () { prefetch(a.href); }, { once: true });
});
```

A few notes about this code:

- It only prefetches links you mark with `data-prefetch`, so you choose which ones.
- It skips visitors who ask to save data, or are on very slow connections. `navigator.connection` is not available in every browser, which is why the code checks that it exists first.
- It stays on your own site, and never repeats a link.
- On touch screens there is no hover, so you might prefetch when a link scrolls into view instead, or on a touch start.

:::info
Newer tools exist for this job. **Speculation rules** let you describe pages to prefetch, or even pre-render, in a block of JSON, and some frameworks and tools prefetch links for you. Support varies, so check current browser support before you depend on them.
:::

## Prefetch and Your Numbers

Prefetch requests are real requests. They show up in your server logs, and some analytics setups may count a prefetched page as a visit. Many browsers add a header to mark them (Chromium uses `Sec-Purpose: prefetch`, for example), which your server can use to tell prefetches from real visits. Check the current documentation for the browsers you care about.

## Checking That It Worked

1. Open DevTools, then **Network**, and load the first page. Look for your prefetched file. It should appear with a low priority.
2. Click through to the next page. The prefetched file should now be loaded **from cache** (look for "disk cache" or "prefetch cache" in the Size column), not downloaded again.
3. Compare the time to load the next page with and without the prefetch.
4. Check that nothing was prefetched that the visitor never saw or could not use.
5. Test with the Network panel throttled, and with data saving on, to see how the code behaves.

## Best Practices

1. **Prefetch the likely, not the possible.**
2. **Keep it small,** or prefetch only the key files.
3. **Use hover or idle triggers** to keep the bet small.
4. **Respect data saving** and slow connections.
5. **Prefetch only public, safe pages.**
6. **Set good caching headers,** so the prefetched file is reusable.
7. **Use analytics to find your real next steps,** not guesses.
8. **Do not prefetch what the current page needs.** Use preload, or put it in the HTML.

## Quick Checklist

- [ ] Each prefetch is for a likely next step
- [ ] Each file is small, or the page is light
- [ ] No action, logout, delete, or private URL is prefetched
- [ ] Data saving and slow connections are respected
- [ ] The prefetched file is cacheable
- [ ] The Network panel shows it used from cache on the next page
- [ ] Analytics and server logs account for prefetch requests

## Security and Privacy Notes

- **A prefetch is a real request.** The server sees it, cookies are sent, and anything the URL does will happen. Never prefetch a link that changes something (logging out, deleting, adding to a basket, confirming). Good design makes such actions a POST request from a button, not a link, but do not rely on that alone.
- **Never prefetch private or one-time URLs,** such as pages with tokens in the address, password reset links, or order confirmations.
- **Do not prefetch personalised pages into shared caches.** Check your cache headers so private pages are never stored where other people can see them.
- **Prefetch can share visitor details with third parties.** Fetching a file from another host tells that host about the visitor. If you need consent before contacting certain services, do not prefetch from them until it is given. Browsers also increasingly keep separate caches per site, so a prefetch from another host may not be reused the way you expect.
- **Respect the visitor's choice.** If they have asked to save data, a prefetch is a poor use of it.

## Global Audience Notes

- **Prefetch costs real money for some visitors.** On pay-as-you-go plans, a guess that misses is not free. Respect data-saving settings, and keep prefetches small.
- **Slow connections gain the most when the guess is right,** and lose the most when it is wrong. Be especially conservative for them.
- **Visitors far from your server feel latency more,** so a prefetch that lands in the cache can help, if the file is small and likely.
- **Test on slow networks and modest phones,** since prefetch competes for the same limited resources.

## Common Mistakes to Avoid

1. **Prefetching everything.**
2. **Prefetching large files or pages.**
3. **Prefetching links that do something,** like logout or delete.
4. **Prefetching private or tokenised URLs.**
5. **Using prefetch for files the current page needs.**
6. **Ignoring data saving.**
7. **Prefetching files that are not cacheable,** so the work is lost.
8. **Not noticing the extra requests in your analytics.**
9. **Prefetching third-party files without thinking about privacy.**
10. **Never checking the next page** to see if the cache was used.

## Key Takeaways

- **Prefetch prepares the next page,** quietly, at low priority.
- **It is a bet.** Make it when the odds are good and the cost is small.
- **Do not use it for what this page needs.** That is preload's job.
- **Never prefetch actions or private URLs.**
- **Respect data saving and slow connections.**
- **Make files cacheable,** and check the next page used the cache.
- **Remember your analytics:** prefetches are real requests.
