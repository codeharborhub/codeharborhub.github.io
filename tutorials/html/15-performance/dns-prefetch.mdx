export function connectionWait(o) {
  const hintAt = 200;
  const total = o.dns + o.tcp + o.tls;
  if (o.needAt <= hintAt) return {none: total, dnsPrefetch: total, preconnect: total};
  return {
    none: total,
    dnsPrefetch: Math.max(0, hintAt + o.dns - o.needAt) + o.tcp + o.tls,
    preconnect: Math.max(0, hintAt + total - o.needAt)
  };
}

          <button type="button" onClick={function () { setChecked(false); setPicked({}); }}>Start again</button>

    </div>
  );
}

# DNS Prefetch in HTML

Before your browser can fetch anything from a server, it has to find that server. Humans use names such as `cdn.example.com`. Computers use numbers. The step that turns one into the other is called a **DNS lookup**, and it takes time, every time the browser meets a new host.

`dns-prefetch` is the smallest resource hint there is. It tells the browser, "do the lookup for this host now, while you have a spare moment." It does nothing else, and costs almost nothing. This lesson shows you what it saves, where it is useful, and why it is often paired with its bigger sibling, `preconnect`.

## What Is DNS?

Think of DNS as the phone book of the internet. You know a name, `cdn.example.com`, and the phone book gives you a number, such as `203.0.113.7`. Only then can your browser "call" the server.

The lookup asks a chain of servers, and the answers are remembered for a while, by the browser, your device, and your internet provider. So a host you have used recently is often quick, and a host you have never used may take longer. The difference can be small (a few milliseconds) or large (hundreds, on a slow or distant network), and it varies a lot.

## The Steps of a New Connection

Fetching a file from a **new** server takes several steps before any data arrives. Each hint covers different steps.

| Step | What happens | `dns-prefetch` | `preconnect` |
| :-- | :-- | :-- | :-- |
| 1. DNS lookup | Find the server's address | Yes | Yes |
| 2. Connect | Open a line to the server | No | Yes |
| 3. Secure handshake | Agree on encryption (for https) | No | Yes |
| 4. Request | Ask for the file | No | No |

So `dns-prefetch` does one step of three. That is why it is so cheap, and also why it saves less. Next lesson, [Preconnect](./preconnect), covers the full set.

## How to Write It

```html
<link rel="dns-prefetch" href="https://cdn.example.com">
```

- **Use the origin only:** the scheme and host, such as `https://cdn.example.com`. A path adds nothing, because DNS cares only about the host.
- **You do not need `crossorigin`.** A lookup is the same however the files are later fetched.
- **Add one line per host,** and keep the list short.

## When to Use It

`dns-prefetch` is a good fit for hosts that are **third-party** (not your own site), and that the page **may need** later, but not at once:

- Analytics and tag managers
- Chat or support widgets
- Embedded videos or maps further down the page
- Social buttons
- Any host that comes up after a script runs

It does nothing for your own site, because the browser has already looked up the host that served the page.

## Pairing It with Preconnect

A very common pattern puts both hints on the same host:

```html
<link rel="preconnect" href="https://cdn.example.com" crossorigin>
<link rel="dns-prefetch" href="https://cdn.example.com">
```

Why both? Browsers that do not understand `preconnect` can still do the DNS lookup, and some browsers limit how many connections they will open early. The lookup acts as a safety net. Check [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel/dns-prefetch) for current browser support of each.

## When It Does Not Help

- **Your own site.** The lookup is already done.
- **Hosts the page never uses.** You pay a small cost for nothing.
- **Hosts used much later.** The answer is only remembered for a limited time, so a lookup that is far ahead of its use may be repeated.
- **Many hosts.** A long list adds noise, and each lookup uses a little battery and network on mobile.
- **A visitor with a fast, warm DNS cache.** The lookup may be nearly free anyway.

Because the cost is so low, a few unneeded `dns-prefetch` hints do little harm. But a careful list is still better than a long one.

## Checking That It Worked

1. Open DevTools, then **Network**, and reload.
2. Click a request to a third-party host, and open the **Timing** tab.
3. Look at **DNS Lookup**. With a good prefetch it may be zero, or not shown, because the lookup already finished.
4. Compare with the same page without the hint. Remember that DNS caching at several levels can hide the difference on a second visit, so clear the cache or use a test tool that starts fresh, such as WebPageTest.
5. Check that you have not hinted any host the page never uses.

## Best Practices

1. **Hint third-party hosts you may use,** not your own.
2. **Use origins only.**
3. **Pair it with `preconnect`** for hosts that matter most.
4. **Keep the list short.**
5. **Remove hints** when you stop using a service.
6. **Do not build hints from untrusted input,** such as user-submitted links.
7. **Test on a fresh cache** and a slow connection.
8. **Measure.** A hint that does not move a number is clutter.

## Quick Checklist

- [ ] Every hinted host is used by the page, or likely to be
- [ ] No hint for your own site
- [ ] Each hint is an origin, with no path
- [ ] Hosts needed immediately use `preconnect`, with `dns-prefetch` as a fallback
- [ ] No hosts that need consent are hinted before consent
- [ ] Old services have had their hints removed
- [ ] DevTools shows the DNS time dropped

## Security and Privacy Notes

- **A lookup tells the network something.** When your page asks for a lookup, the visitor's DNS resolver (often their internet provider) learns that this page uses that host. A hint triggers the lookup earlier, and for hosts the visitor may never actually use. If you need consent before contacting certain third parties (analytics or advertising, for example), do not hint those hosts until consent is given. This is not legal advice, so check the rules that apply to you.
- **Never create hints from untrusted input.** If a page turns a user-submitted link into a `dns-prefetch`, the visitor's browser looks up a host chosen by someone else, which can be used to track visitors. Generate hints only from a list you control.
- **Only hint hosts you trust.** Even a lookup is a small way of reaching out.
- **Encrypted DNS** (offered by some browsers and providers) hides lookups from people on the network, but not from the resolver. It is the visitor's choice, not something your HTML controls.

## Global Audience Notes

- **DNS speed varies a lot by country, provider, and network.** Visitors on slow or distant networks may see lookups of hundreds of milliseconds, so they gain most from an early lookup.
- **Third-party hosts can be slow, or blocked, in some places.** A page must still work if a host never answers, so never make the page depend on a hinted service.
- **Mobile networks pay a price for every lookup,** in time and battery. A short list is kind to them.
- **Test from different regions,** using a tool such as WebPageTest, since DNS behaviour differs around the world.

## Common Mistakes to Avoid

1. **Hinting your own site.**
2. **Including a path** and thinking it matters.
3. **Hinting dozens of hosts.**
4. **Hinting hosts the page never uses.**
5. **Using `dns-prefetch` for a host needed straight away** when `preconnect` would save more.
6. **Hinting before consent** for services that need it.
7. **Building hints from user input.**
8. **Leaving hints for services you stopped using.**
9. **Adding `crossorigin`,** which is not needed for DNS lookups.
10. **Assuming it always helps,** without testing on a fresh cache.

## Key Takeaways

- **DNS turns a host name into an address,** and it takes time for each new host.
- **`dns-prefetch` does just that step, early.** It is cheap, and saves less.
- **Use it for third-party hosts you may need,** and `preconnect` for those you need at once.
- **Origins only, no `crossorigin`.**
- **Keep the list short,** and remove hints you no longer need.
- **Mind privacy:** wait for consent where it is needed, and never hint untrusted hosts.
- **Measure** the DNS time in DevTools, on a fresh cache.
