export function simulateLoad(options) {
  const ttfb = 200;
  const htmlDone = 300;
  const cssStart = 220;
  const cssDone = cssStart + 300;
  const scriptStart = 230;
  const scriptDownloaded = scriptStart + 400;
  const scriptReady = scriptDownloaded + 150;
  let fcp = Math.max(htmlDone, cssDone);
  if (options.script === "blocking") fcp = Math.max(fcp, scriptReady);
  let heroStart;
  if (options.preloadHero) heroStart = ttfb + 5;
  else if (options.hero === "html") heroStart = 240;
  else if (options.hero === "css") heroStart = cssDone;
  else heroStart = cssDone + 100;
  const heroDone = heroStart + 700;
  const lcp = Math.max(fcp, heroDone);
  const connectDone = options.preconnect ? ttfb + 5 + 400 : null;
  const tagStart = options.preconnect ? Math.max(scriptReady, connectDone) : scriptReady + 400;
  const tagDone = tagStart + 300;
  const bars = [
    {id: "html", label: "HTML document", start: 0, end: htmlDone},
    {id: "css", label: "styles.css (in the head)", start: cssStart, end: cssDone},
    {id: "js", label: "app.js (" + options.script + ")", start: scriptStart, end: scriptDownloaded},
    {id: "jsrun", label: "app.js runs", start: scriptDownloaded, end: scriptReady},
    {id: "hero", label: "Hero image" + (options.preloadHero ? " (preloaded)" : ""), start: heroStart, end: heroDone},
  ];
  if (options.preconnect) bars.push({id: "conn", label: "Connection to the tag server", start: ttfb + 5, end: connectDone});
  bars.push({id: "tag", label: "Third-party tag" + (options.preconnect ? "" : " (connects first)"), start: tagStart, end: tagDone});
  return {bars, fcp, lcp, scriptReady, tagDone};
}

A page can be beautiful, accurate, and well built, and still lose its visitors in the first few seconds. People do not wait. On a slow phone in a moving train, every extra second is a chance for someone to give up, and every kilobyte costs real money for someone on a limited data plan.

**Performance** is how quickly and how smoothly your page loads and responds. A surprising amount of it is decided by **plain HTML:** which files you ask for, in what order, with which attributes. This section teaches you those choices, one at a time, and how to **measure** whether they worked.

## Why Performance Matters

- **People leave slow pages.** Studies by large sites have repeatedly linked faster pages to more completed visits and purchases. The exact numbers vary, so measure your own site.
- **Not everyone has a fast phone or network.** A page that is fine on your laptop may be painful on a mid-range phone on a weak signal.
- **Data costs money.** Heavy pages are expensive for people on limited plans.
- **Speed is part of accessibility.** Long freezes and jumping layouts are hardest on people who use assistive technology, have motor or cognitive difficulties, or need more time.
- **Search engines notice.** Page experience is one of many signals, and a small one next to content quality. See [HTML SEO Basics](/html/seo/html-seo-basics).
- **It saves energy.** Less data and less work means less power used, on both the server and the device.

## How a Browser Loads a Page

In very simple terms:

1. **Request.** The browser asks the server for the HTML, and waits for the first byte (the **time to first byte**).
2. **Parse.** It reads the HTML from top to bottom, and **discovers** other files to fetch: stylesheets, scripts, images, fonts.
3. **Fetch.** It downloads those files, often several at once, on connections it may need to open first (a DNS lookup, a TCP connection, and encryption).
4. **Build.** It combines the HTML and the CSS, works out the layout, and **paints** the page.
5. **Run.** It runs JavaScript, which can change the page, and respond to the visitor.

At each step, something can **wait on something else.** Performance work is mostly about **removing the waiting.**

### What blocks the page

| Thing | What it blocks | Typical fix |
| :-- | :-- | :-- |
| **A stylesheet in the head** | Painting the page (the browser will not draw without the styles) | Keep CSS small, and load only what is needed first |
| **A plain script** | Reading the rest of the HTML while it downloads and runs | Use `defer` or `async` |
| **A late-found important file** | The picture or font arriving when it is needed | `preload`, or put it in the HTML |
| **A new connection to another server** | The first request to it | `preconnect` |
| **A large, unneeded file** | Bandwidth for everything else | Smaller files, lazy loading, responsive images |

## What We Measure

Three numbers, called the **Core Web Vitals,** describe the experience people have:

| Metric | What it measures | Good means |
| :-- | :-- | :-- |
| **LCP** | How soon the biggest visible thing appears | Up to 2.5 seconds |
| **INP** | How quickly the page responds when you use it | Up to 200 milliseconds |
| **CLS** | How much the layout jumps while loading | Up to 0.1 |

These are the thresholds Google published at the time of writing, and they may change. Check your own pages, and test your understanding:

### Lab data and field data

- **Lab data** comes from a test you run, on one device, on one connection: Lighthouse, PageSpeed Insights, WebPageTest, and the browser's developer tools. It is repeatable, and good for finding causes.
- **Field data** comes from real visitors on their real devices: Search Console's Core Web Vitals report, and real user monitoring. It shows what people actually experience, and is what matters most.

A good habit is to **find** problems with lab tests, and **confirm** with field data.

## How to Measure

You cannot improve what you do not measure. These tools are free, and a good place to start:

- **Lighthouse,** built into Chrome DevTools. It tests one page, and suggests fixes.
- **PageSpeed Insights.** It runs Lighthouse, and also shows **field data** for popular pages, where available.
- **Chrome DevTools, Network panel.** It shows every file, when it started, and how long it took (the waterfall).
- **Chrome DevTools, Performance panel.** It shows what the browser did, and when.
- **WebPageTest.** It tests from different places, devices, and connection speeds.
- **Search Console's Core Web Vitals report.** It shows real-visitor data for your whole site.

Habits that make your tests honest:

1. **Throttle the network and the CPU** in DevTools. Your development machine is probably much faster than your visitors'.
2. **Test a cold load** (an empty cache), and a repeat load.
3. **Test on a real mid-range phone** when you can.
4. **Run each test several times,** since results vary.
5. **Change one thing at a time,** so you know what helped.

## Five Habits to Start Today

1. **Send less.** Smaller images, fewer scripts, and no files you do not use.
2. **Put the important things first.** The main image, the main styles, and the main script.
3. **Do not block.** Use `defer` or `async` for scripts.
4. **Reserve space.** Give images and embeds a `width` and `height`, so the page does not jump.
5. **Measure.** Check Lighthouse and your field data, not your feelings.

## Performance Checklist for Any Page

- [ ] The page works with a slow connection and a slow phone
- [ ] CSS in the head is small, and only what is needed first
- [ ] Scripts use `defer` or `async`, not plain blocking tags
- [ ] The main image is found early, not lazy-loaded, and not too big
- [ ] Images below the first screen use `loading="lazy"`
- [ ] Every image and embed has a `width` and `height`
- [ ] Images use modern formats and responsive sizes
- [ ] Connections to other servers use `preconnect` only when they are needed
- [ ] No unused scripts, styles, or fonts
- [ ] Core Web Vitals checked in the lab and in the field

## Security and Privacy Notes

- **Third-party scripts are a risk.** Every analytics, chat, ad, or widget script runs with the full power of your page. A compromised or careless provider can read what visitors type, or change your page. Use only what you need, from providers you trust, and consider the `integrity` attribute for files that do not change.
- **Hints contact other servers early.** `preconnect` and `dns-prefetch` make the visitor's browser contact a third party before the visitor does anything, which shares their address and some details with that party. If you need consent first (for example for analytics or advertising services), do not hint those hosts until consent is given. This is not legal advice, so check the rules that apply to you.
- **Preload and prefetch only public resources.** Do not hint at private, personal, or one-time URLs. A prefetched address is fetched whether or not the visitor ever goes there, and can trigger actions or appear in logs.
- **Measuring collects data.** Real user monitoring records things about your visitors' devices and pages. Collect the least you need, say what you collect, and respect consent rules.
- **Caching can leak.** Do not let private or personalised pages be stored by shared caches. Check your cache headers.
- **A content security policy** can limit which hosts can load scripts, which also stops a hint pointing at an unexpected host from helping an attacker.

## Global Audience Notes

- **Many of your readers are on slow networks and modest phones.** Design for them first, and everyone else gets a bonus.
- **Data is expensive in many places.** Heavy pages and autoplaying media can cost people real money. Offer lighter options, and respect the `Save-Data` preference where supported.
- **Distance adds delay.** A **content delivery network (CDN)** serves files from near your readers, and is one of the biggest wins for a worldwide audience.
- **Scripts add weight.** Fonts for Chinese, Japanese, and Korean can be very large, so use subsets, system fonts, or only the weights you need.
- **Third-party services may be slow, or blocked, in some countries.** A page should still load if a widget does not.
- **Test from other places.** WebPageTest and similar tools can run from different regions and on different connections.
- **Use plain, small, well-compressed files,** so the page works on older browsers and devices too.

## Common Mistakes to Avoid

1. **Optimising before measuring.**
2. **Lazy-loading the main image,** which makes the page seem slower.
3. **Plain scripts in the head** that block the page.
4. **Preloading everything,** which then competes with the files that matter.
5. **Preconnecting to many hosts** you barely use.
6. **Huge images,** displayed small.
7. **No `width` and `height`,** so the layout jumps.
8. **Too many third-party scripts.**
9. **Testing only on a fast machine and a fast connection.**
10. **Trusting a single score** instead of looking at what the page does.
11. **Making a change, and never checking** that it helped.
12. **Forgetting repeat visits,** where caching changes everything.

## Quick Recap

Click a question to check your answer.

<details>
<summary>1. What is web performance?</summary>

How quickly and smoothly a page loads and responds. Much of it is decided by which files the HTML asks for, in what order, and with which attributes.

</details>

<details>
<summary>2. What blocks a page from appearing?</summary>

Stylesheets in the head, and plain scripts that stop the browser reading the rest of the HTML while they download and run. Late-found important files and slow connections also delay things.

</details>

<details>
<summary>3. What are the three Core Web Vitals?</summary>

LCP (how soon the biggest thing appears), INP (how quickly the page responds), and CLS (how much the layout jumps).

</details>

<details>
<summary>4. What is the difference between lab data and field data?</summary>

Lab data comes from a test you run on one device and connection. Field data comes from real visitors. Find problems with lab tests, and confirm with field data.

</details>

<details>
<summary>5. Which scripts should use defer or async?</summary>

Almost all of them. Use `defer` for scripts that need the page and must run in order, and `async` for independent scripts such as analytics.

</details>

<details>
<summary>6. Why should you test with throttling?</summary>

Your own machine and network are probably much faster than your visitors'. Throttling shows what a slower phone and connection experience.

</details>

## Key Takeaways

- **Performance is about removing waiting:** for files to be found, fetched, and run.
- **HTML decides a lot:** what you load, in what order, and how.
- **Do not block the page.** Use `defer` and `async`.
- **Help the browser find important files early,** with the right element or a preload.
- **Do not load what is not needed,** and do not send more than the screen needs.
- **Reserve space** for images and embeds with `width` and `height`.
- **Measure in the lab and in the field,** and check that each change helped.
- **Design for slow networks and modest phones first.**
