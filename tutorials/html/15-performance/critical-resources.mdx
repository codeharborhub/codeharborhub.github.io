export function simulateCritical(o) {
  const start = 120;
  const htmlDone = 300;
  const css1Done = start + 300;
  const fontsCssDone = o.flatten ? start + 200 : css1Done + 200;
  const cssFull = Math.max(css1Done, fontsCssDone);
  const cssDone = o.inlineCss ? htmlDone : cssFull;
  const scriptEnd = start + 400 + 100;
  let fcp = Math.max(htmlDone, cssDone);
  if (!o.deferScript) fcp = Math.max(fcp, scriptEnd);
  const fontFile = o.preloadFont ? start + 300 : fontsCssDone + 300;
  const fontReady = Math.max(fontFile, cssDone);
  const heroFound = o.inlineCss ? htmlDone : css1Done;
  const heroReady = o.preloadHero ? start + 500 : heroFound + 500;
  const lcp = Math.max(fcp, heroReady);
  const fontChain = o.preloadFont ? 2 : (o.flatten ? 3 : 4);
  const heroChain = o.preloadHero || o.inlineCss ? 2 : 3;
  const cssChain = o.flatten ? 2 : 3;
  return {fcp: fcp, fontReady: fontReady, lcp: lcp, chain: Math.max(fontChain, heroChain, cssChain)};
}

# Critical Resources in HTML

A page can contain hundreds of files, but only a handful decide how fast it feels. Those few are the **critical resources**: the files the browser must have before it can show something useful.

Performance work is largely a hunt for them. Once you know which files are critical, you can make them small, find them early, and stop everything else from getting in their way. This lesson shows you how to find them and how to shorten the path they take.

## What You Will Learn

- What makes a resource critical
- What the critical rendering path is

- Which resources block painting, and how to unblock them
- Techniques: flattening, inlining, `media`, `defer`, fonts, and preload
- How to find your own critical resources in DevTools

## The Big Idea

Think of the first screen as a meal, and the critical resources as the ingredients without which you cannot serve anything. Everything else is a side dish: it can arrive later.

</head>

## What Makes a Resource Critical?

Ask three questions about any file:

1. **Does the browser need it before it can paint?** CSS in the head and plain scripts do. These are **render-blocking**.
2. **Is it part of the first screen?** The main image, the headline font, and the logo are.
3. **Does something else wait for it?** A stylesheet that imports another one makes the second file critical too.

A file that answers "no" to all three can wait, or be lazy, deferred, or removed.

## The Critical Rendering Path

The critical rendering path is the sequence of steps from "the browser got the HTML" to "pixels on the screen":

1. Read the HTML and build the page structure.
2. Fetch and read the CSS, then work out how everything looks.
3. Run any blocking scripts.
4. Lay out the page and paint it.

Every file in those steps is on the critical path. The **length** of the path matters in two ways: how many bytes it carries, and how many separate steps, one after another, it needs.

## Chains Are the Hidden Cost

Files that can be fetched side by side cost roughly the time of the slowest one. Files that must be fetched one **after another** cost the **sum** of their times, plus a delay for each hand-off.

Here is a typical chain:

```text
index.html  ->  site.css  ->  fonts.css (via @import)  ->  inter.woff2
```

The browser cannot know about `fonts.css` until it has read `site.css`, and cannot know about the font file until it has read `fonts.css`. Each link in the chain adds a full round trip to the server. On a slow or distant connection, round trips are the most expensive thing there is.

The cure is to **make chains shorter and wider**: get files discovered in the HTML, where the browser finds them immediately and can fetch them in parallel.

## What Blocks, and How to Unblock

| Resource | What it blocks | How to unblock |
| :-- | :-- | :-- |
| CSS in the head | The first paint | Keep it small, inline the critical part, split out the rest |
| A plain script | Reading the rest of the HTML | Use `defer` or `async` |
| `@import` in CSS | The CSS, and what depends on it | Use a `link` element instead |
| A web font | Text in that font, or it swaps late | Preload, host it close, and use `font-display` |
| A CSS background image | Found only after the CSS is read | Preload it, or use an `img` element |
| A third-party stylesheet | The first paint, if it is in the head | Host it yourself, or load it later |

## Seven Techniques

### 1. Flatten the chain

Replace `@import` with `link` elements in the HTML, so the browser finds every file at once.

```html
<!-- Before: site.css contains  @import url("fonts.css");  -->
<link rel="stylesheet" href="/css/site.css">

<!-- After: both are found immediately -->
<link rel="stylesheet" href="/css/fonts.css">
<link rel="stylesheet" href="/css/site.css">
```

### 2. Inline the critical CSS

Put the few rules the first screen needs directly inside a `style` element, so the first paint does not wait for a CSS file. Keep it small: a commonly quoted rule of thumb is to keep the whole first response within roughly 14 KB compressed, so it arrives in the first round trip, but treat that as a guide and measure. Remember that inline CSS is repeated on every page and cannot be cached on its own, so it is a trade-off, and works best for a short, stable set of rules. Many build tools can extract critical CSS for you.

### 3. Do not let unneeded CSS block

A stylesheet with a `media` value that does not match the current screen is not render-blocking. Browsers still download it, usually at a lower priority.

```html
<link rel="stylesheet" href="/css/print.css" media="print">
<link rel="stylesheet" href="/css/wide.css" media="(min-width: 1200px)">
```

The "print then switch to all" trick in the code above uses the same idea to load the rest of your CSS without blocking. It needs JavaScript (hence the `noscript` fallback), and an inline `onload` may conflict with a strict content security policy. It can also cause a brief flash if the rest of the CSS styles things on the first screen, so check carefully.

### 4. Defer scripts

Use `defer` for your own scripts and `async` for independent ones, as covered in [Script Loading](./script-loading), [Defer](./defer), and [Async](./async).

### 5. Treat fonts with care

A font file is discovered late, because it is named inside CSS. Help the browser:

- **Preload** the one or two files the headline needs, with `crossorigin` (see [Preload](./preload)).
- **Preconnect** if the font comes from another host (see [Preconnect](./preconnect)).
- **Use `font-display: swap`** in your `@font-face`, so text shows in a fallback font at once and swaps when the font arrives. There is a short change of look, so test how it feels.
- **Use fewer files and weights,** and subset large fonts.
- **Consider hosting fonts yourself,** which removes a third-party connection from the critical path.

### 6. Preload what is found late

For the hero image set in CSS, or any critical file the browser discovers late, a [preload](./preload) starts the download earlier. Use it sparingly.

### 7. Remove what you do not need

The fastest critical resource is the one that is not there. Delete unused CSS, unused fonts, and old scripts.

Then find the real ones on your own pages:

1. Open DevTools, then **Network**, and reload on a throttled connection.
2. Look at the **Waterfall**, and find the files that start late. A file that starts only after another finishes is part of a chain.
3. Click a file and open its **Initiator** to see what caused it to load.
4. Check the **Priority** column. High priority files are the ones the browser thinks are critical.
5. Run **Lighthouse** and read the suggestions about render-blocking requests and chained critical requests. Names of audits change over time, so read the descriptions.
6. Open the **Performance** panel, and watch which files stand between navigation and the first paint.
7. Use the **Coverage** tool to see how much CSS and JavaScript the page does not use.

## Best Practices

1. **Know your critical resources.** Write the list down for each key page.
2. **Keep the list short,** and each file small.
3. **Shorten chains.** Get files discovered in the HTML.
4. **Never use `@import`** for important CSS.
5. **Defer scripts,** and keep third-party code off the critical path.
6. **Give fonts special care:** preload, host close, and use `font-display`.
7. **Preload only what is late-found and important.**
8. **Measure on a slow connection,** since chains hurt most there.

## Quick Checklist

- [ ] The critical resources for the first screen are known
- [ ] No `@import` for important CSS
- [ ] CSS in the head is small, with the critical part inlined if it helps
- [ ] Non-critical CSS does not block the first paint
- [ ] Scripts use `defer` or `async`
- [ ] Fonts are few, preloaded if critical, and use `font-display`
- [ ] The hero image is found early, and not lazy
- [ ] No third-party stylesheet in the head that you do not control
- [ ] The waterfall shows no long chains

## Security and Privacy Notes

- **Critical third-party files are a single point of failure.** If a font or stylesheet host is slow or down, your first paint waits for it. Hosting critical files yourself is both faster and more reliable.
- **Third-party hosts see your visitors.** Fonts and styles from another host share the visitor's address and some details with it. Self-hosting avoids this. If you must use one, load it in line with the rules that apply to you. This is not legal advice.
- **Inline CSS and inline handlers can clash with a content security policy.** A strict policy blocks inline styles and `onload` attributes unless you allow them with a nonce or hash. Plan for this if you inline critical CSS.
- **Use integrity hashes for fixed third-party files.** The `integrity` attribute lets the browser reject a file that has been altered.
- **Preloads contact hosts early.** Do not preload from hosts that need consent first.

## Global Audience Notes

- **Round trips cost more where latency is high.** Visitors far from your servers, on mobile networks, or on satellite links pay for every step in a chain. Short chains and a nearby CDN help them most.
- **Self-hosted fonts save a connection** to another country's servers, and avoid problems where a font host is slow or blocked.
- **Fonts for some scripts are large.** Chinese, Japanese, and Korean fonts can be very big. Subset them, use system fonts for body text, or keep web fonts for headings only.
- **Test on slow connections and modest phones.** What is critical on a fast laptop is not always the same as on a slow phone.
- **Keep the page useful** without the extras: text should be readable even before the custom font arrives.

## Common Mistakes to Avoid

1. **`@import` chains** for important CSS.
2. **A huge CSS file** where most rules are unused.
3. **Plain scripts in the head.**
4. **A web font discovered late,** with no preload.
5. **A hero image hidden in CSS** with no preload.
6. **Third-party stylesheets in the head** that you do not control.
7. **Inlining far too much CSS,** so every page is heavy.
8. **Preloading everything,** so nothing stands out.
9. **Splitting CSS carelessly,** so the first screen flashes unstyled.
10. **Only testing on a fast connection.**

## Key Takeaways

- **A few files decide how fast the page feels.** Find them first.
- **Chains cost the sum of their steps.** Make them shorter and wider.
- **CSS in the head and plain scripts block painting.** Keep CSS small, and defer scripts.
- **Fonts and CSS backgrounds are found late.** Preload them, or move them into the HTML.
- **Host critical files yourself** where you can, for speed, reliability, and privacy.
- **Remove what you do not need.**
- **Measure on slow connections,** and re-check after every change.
