  const [buggy, setBuggy] = useState(false);
  const [open, setOpen] = useState(false);
  const [pressed, setPressed] = useState(false);
  const [tab, setTab] = useState(0);

  const box = {border: "1px solid #94a3b8", borderRadius: "8px", padding: "0.7rem", marginBottom: "0.6rem"};
  return (
    <div>
      <p style={{margin: "0 0 0.6rem"}}>

      </div>
      <div style={box}>
        <p style={{margin: "0 0 0.4rem"}}><strong>Toggle button</strong></p>
        <button type="button" aria-pressed={told.pressed} onClick={() => setPressed(!pressed)} style={{fontWeight: pressed ? 700 : 400, background: pressed ? "#dbeafe" : undefined, color: pressed ? "#1e293b" : undefined, border: pressed ? "2px solid #1d4ed8" : undefined}}>

export function checkValue(item, raw) {
  const value = raw.trim();
  if (item.values) {
    if (value === "") return {ok: false, text: "The value is empty. Allowed: " + item.values.join(", ") + "."};
    if (item.values.indexOf(value) === -1) return {ok: false, text: "Not valid. Allowed: " + item.values.join(", ") + (item.values.indexOf(value.toLowerCase()) !== -1 ? ". Write the value in lowercase." : ".")};
    return {ok: true, text: "Valid."};
  }
  if (item.type === "number") return !isNaN(Number(value)) && value !== "" ? {ok: true, text: "Valid."} : {ok: false, text: "This must be a number, such as 40."};
  if (item.type === "integer") return /^\d+$/.test(value) ? {ok: true, text: "Valid."} : {ok: false, text: "This must be a whole number, such as 2."};
  if (item.type === "string") return value === "" ? {ok: false, text: "An empty label gives nothing to announce."} : {ok: true, text: "Valid. Remember to translate it."};
  if (value === "") return {ok: false, text: "This needs at least one id."};
  return {ok: true, text: "Valid, as long as an element with " + (value.indexOf(" ") !== -1 ? "each of these ids" : "the id \"" + value + "\"") + " exists in the page."};
}

HTML elements have built-in meaning, and the browser keeps track of their state for you. A checkbox knows whether it is checked. A `details` knows whether it is open. A `button` that is `disabled` is understood as unavailable. Whenever possible, use these.

But when you build something custom, the browser cannot know what you mean. That is the job of ARIA **states** and **properties:** small attributes that tell assistive technology **what is happening to a thing,** and **how things relate to one another.** They are simple to write, and **easy to get out of date,** which is where most mistakes come from.

## States and Properties

ARIA splits its attributes into two groups. In practice the line is fuzzy, and you rarely need to care which is which. The idea behind it is useful, though:

| | States | Properties |
| :-- | :-- | :-- |
| **What they describe** | Something that changes as people use the page | Something that is fixed, or changes rarely |
| **Who changes them** | Your script, often | Usually you, once, in the HTML |
| **Examples** | `aria-expanded`, `aria-pressed`, `aria-checked`, `aria-selected`, `aria-current`, `aria-disabled`, `aria-invalid`, `aria-busy`, `aria-hidden` | `aria-label`, `aria-labelledby`, `aria-describedby`, `aria-controls`, `aria-haspopup`, `aria-required`, `aria-orientation`, `aria-level` |

You can think of a **property** as **"what it is like,"** and a **state** as **"what it is doing right now."**

## What Values Look Like

ARIA attributes take a few kinds of values. Getting the kind right matters, because browsers **ignore** a value they do not understand.

| Kind | What it looks like | Examples |
| :-- | :-- | :-- |
| **True or false** | The words `true` or `false`, in quotes | `aria-disabled="true"` |
| **Tri-state** | `true`, `false`, or `mixed` | `aria-checked="mixed"` |
| **Token** | One word from a fixed list | `aria-live="polite"`, `aria-current="page"` |
| **ID reference** | The `id` of another element | `aria-labelledby="title"` |
| **ID reference list** | Several ids, with spaces | `aria-describedby="hint error"` |
| **String** | Plain text, in the page language | `aria-label="Close"` |
| **Number or integer** | A number | `aria-valuenow="40"`, `aria-level="2"` |

A few more notes:

- **Write `true` and `false` as words,** not `yes`, `on`, or `1`.
- **Write values in lowercase,** to be safe.
- **A missing attribute and `false` are not always the same.** For `aria-pressed`, a missing attribute means "this is not a toggle," and `false` means "a toggle that is off." Follow the rules for each one.
- **IDs must exist,** and be unique on the page.

## The Big Trap: Keeping State in Sync

An ARIA state is a **promise about the page right now.** If the panel is open and the attribute says `false`, ARIA is **lying** to the person who relies on it. Unlike a visual bug, nobody using a screen reader can see the mismatch to report it. They simply get confused.

Some ways to avoid it:

1. **Update the state in the same place you update the page.** The line that opens the panel is also the line that sets `aria-expanded`.
2. **Use one source of truth.** In a framework, bind the attribute to your state variable (`aria-expanded={open}`), so they can never disagree.
3. **Style from the attribute.** If your CSS uses `[aria-expanded="true"]` to show the open look, then a forgotten attribute is also a visible bug, and gets fixed quickly:

```css
button[aria-expanded="true"] .chevron {
  transform: rotate(180deg);
}

[role="tab"][aria-selected="true"] {
  border-bottom: 3px solid #1d4ed8;
}
```

4. **Test every state change** with a screen reader, or the Accessibility panel, and not only by looking.
5. **Set the starting state** in the HTML, so the page is right before any script runs.

## Put It on the Right Element

A state belongs on the element a person **interacts with,** or that has that role:

| Attribute | Put it on | Not on |
| :-- | :-- | :-- |
| `aria-expanded` | The button that opens the panel | The panel |
| `aria-selected` | The `tab` | The `tabpanel` |
| `aria-pressed` | The toggle `button` | A wrapper `div` |
| `aria-current` | The link or step that is current | The whole list |
| `aria-invalid` | The form field | The error message |
| `aria-busy` | The region being updated | The button that started it |

## The States You Will Use Most

### `aria-expanded`

For anything that **opens and closes:** a menu button, an accordion header, a disclosure. It goes on the **trigger.** (If you can, use the native `details` and `summary`, which need none of this.)

### `aria-pressed`

For a **toggle button** that is on or off (Mute, Bold, Favourite). Keep the label the same, and let the state do the changing. Use `mixed` for a "select all" button when only some items are selected.

### `aria-checked`

For **custom** checkboxes, radios, and switches. For a **native** checkbox, do **not** add it, because the browser already tracks `checked`, and the two can disagree.

### `aria-selected`

For the chosen item in a set of **tabs,** **options,** or **rows.** Exactly one tab in a tab list should be selected at a time.

### `aria-current`

For **where you are:** `page` for the current page link in a menu, `step` for the current step in a process, `location`, `date`, and `time` for other cases, and `true` if none fit. Do not rely on a colour or a bold style alone, because a screen reader cannot see them.

### `aria-disabled`

Says a control is **unavailable,** but leaves it **focusable.** You must block the action yourself, and make it look unavailable. For plain form controls, the native `disabled` attribute is simpler. See [Accessible Buttons](./accessible-buttons) for when to choose which.

### `aria-invalid`

Marks a field with a **problem.** Set it to `true` when the field has an error, together with a visible error message linked by `aria-describedby`. Remove it (or set it to `false`) once the problem is fixed. See [Accessible Forms](./accessible-forms).

### `aria-busy`

Says a region is **being updated,** so a screen reader can wait until it finishes, rather than reading half-loaded content. Support is uneven, so also give a visible message, and a `role="status"` announcement, as in the lab below.

### `aria-hidden`

Removes something from assistive technology completely. It has its own lesson, because it is easy to misuse: [aria-hidden](./aria-hidden).

## Properties You Will Use Often

- **`aria-label`, `aria-labelledby`, `aria-describedby`:** names and descriptions. Each has its own lesson soon.
- **`aria-controls`:** says which element a control changes. Support in screen readers is limited, so treat it as a helper. The real work is done by good structure, and by `aria-expanded`.
- **`aria-haspopup`:** says a control opens a menu, a list, or a dialog. Support varies, so use it with `aria-expanded`, not instead of it.
- **`aria-required`:** for custom widgets. For native fields, use `required`.
- **`aria-orientation`:** says whether a toolbar, tab list, or slider is `horizontal` or `vertical`.
- **`aria-level`:** the heading level of a custom heading, or the depth of a tree item.
- **`aria-valuenow`, `aria-valuemin`, `aria-valuemax`, `aria-valuetext`:** for sliders and progress bars. Use `aria-valuetext` when the number needs a unit or a word ("3 stars," "Medium").

## Native and ARIA: Do Not Fight

When both a native feature and an ARIA attribute describe the same thing, **the native one is the truth.** A `checkbox` with `checked` and `aria-checked="false"` is confusing, and browsers do not agree on which wins. A button with `disabled` and `aria-disabled="false"` is just as odd.

- **Use the native attribute** (`checked`, `disabled`, `required`, `hidden`, `open`) whenever one exists.
- **Add the ARIA state only** where HTML has none (`aria-expanded` on a custom button, `aria-selected` on a tab, `aria-current`).
- **Never set both,** and never let them disagree.

## Good Habits

1. **Use native states first** (`checked`, `disabled`, `required`, `open`).
2. **Keep ARIA states in sync** with what people see, from one source of truth.
3. **Put each attribute on the right element.**
4. **Write values correctly:** lowercase `true` and `false`, real tokens, real ids.
5. **Set the starting state in the HTML.**
6. **Style from the attribute,** so mistakes show.
7. **Keep labels stable** when a state changes.
8. **Back every ARIA state with a visible cue,** and every visible cue with a state.
9. **Test with a screen reader.**

## Accessibility Checklist

- [ ] Every toggle, disclosure, tab, and custom checkbox has the right state attribute.
- [ ] States change at the same moment as the page does.
- [ ] Starting states are correct in the HTML.
- [ ] State attributes are on the correct elements.
- [ ] Values are valid, in lowercase, with real tokens.
- [ ] Every id in `aria-controls`, `aria-labelledby`, and `aria-describedby` exists.
- [ ] No native control also has a disagreeing ARIA state.
- [ ] `aria-current` marks the current page or step.
- [ ] Errors use `aria-invalid` and a visible message, and clear when fixed.
- [ ] Loading regions give a visible and spoken message as well as `aria-busy`.

## Security and Privacy Notes

- **State attributes are public.** Anyone can read `aria-*` values in the page source, and assistive technology reads them aloud. Do not store secrets, personal data, or tokens in them.
- **Do not expose private information through state.** An `aria-invalid="true"` on a login field, or a "valid" and "invalid" announcement on a password check, could reveal something about an account, so keep messages general ("Email or password is incorrect").
- **States must tell the truth.** A state that says "selected" or "checked" when it is not, or a loading state used to hide content, is deceptive and can lead people to take actions by mistake.
- **Be careful with consent controls.** A toggle for tracking or marketing must report its **real** state, so that people using assistive technology know what they have agreed to.
- **Do not use state to profile people.** How someone uses states and focus can reveal that they use assistive technology, and so reveal a disability.
- **Keep ids unpredictable where it matters.** Reusing the same ids for sensitive elements across pages makes automation (and scraping) easier, though this is a minor concern next to correct markup.

## Global Audience Notes

- **Translate string values** (`aria-label`, `aria-valuetext`, `aria-description`) with the rest of your page. States such as `true` and `false` are code, and are never translated.
- **Format `aria-valuetext` for the reader.** Numbers, units, and dates differ by region ("3,5 stars" or "3.5 stars"), so build the text with a locale-aware formatter.
- **Right-to-left languages:** `aria-orientation` and arrow-key behaviour in tabs and sliders should follow the reading direction. Test them in a right-to-left layout.
- **Screen readers announce states in the user's own language,** such as "expanded," "pressed," and "selected." Do not write these words into your labels, because the user would hear them twice.
- **Slow connections:** a loading state (`aria-busy` with a visible message) is more important when pages take a while to update. Say what is happening, in short, translatable words.
- **Different tools differ.** Support for states such as `aria-busy`, `aria-haspopup`, and `aria-controls` varies. Test on the devices and screen readers your audience uses.

## Common Mistakes to Avoid

1. **Never updating the state** after the page changes.
2. **`aria-expanded` on the panel,** not the button.
3. **Invalid values** such as `aria-expanded="yes"`.
4. **`aria-checked` on a native checkbox.**
5. **Both `disabled` and `aria-disabled`.**
6. **`aria-selected` on every tab,** or on none.
7. **Changing the label and the state together,** such as "Unmute" with `aria-pressed`.
8. **Pointing `aria-controls` at an id that does not exist.**
9. **Relying on `aria-busy` alone** to tell people something is loading.
10. **Using `aria-current` without any visible cue,** or the other way round.
11. **Writing the state words in the label** ("Menu, expanded").
12. **Never checking the Accessibility panel.**

## Quick Recap

Click a question to check your answer.

<details>
<summary>1. What is the difference between a state and a property?</summary>

A state describes something that changes as people use the page (`aria-expanded`, `aria-pressed`). A property describes something fixed or rarely changing (`aria-label`, `aria-controls`).

</details>

<details>
<summary>2. Why must you keep ARIA states in sync with the page?</summary>

The state is the only way a screen reader user knows what changed. If it is out of date, they are told something false.

</details>

<details>
<summary>3. Which element gets `aria-expanded`?</summary>

The control that opens and closes the content (usually a `button`), not the content panel.

</details>

<details>
<summary>4. When should you not use `aria-checked`?</summary>

On a native checkbox or radio button. The browser already tracks `checked`, and the two can disagree.

</details>

<details>
<summary>5. What does `aria-current="page"` do?</summary>

It marks the link to the page you are on, so a screen reader can say "current page." It needs a visible cue as well.

</details>

<details>
<summary>6. What happens if you write an invalid value, like `aria-expanded="yes"`?</summary>

Browsers do not warn you. They ignore the value, or treat it unpredictably, so the state is lost.

</details>

## Key Takeaways

- **States** describe what is happening now. **Properties** describe what it is like and how things relate.
- **Use native states first,** and ARIA only to fill gaps.
- **Keep every state in sync** with the page, from one source of truth.
- **Put each attribute on the right element:** the trigger, the tab, the field.
- **Use valid values:** lowercase `true` and `false`, real tokens, real ids.
- **Pair every ARIA state with a visible cue,** and every visible cue with an ARIA state.
- **Check in the Accessibility panel,** and test with a screen reader.
