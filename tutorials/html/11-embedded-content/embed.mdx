For a long time, the web could not do everything by itself. To show an animation, a rich game, or a special document, a page needed a **plug-in**: a separate program that the visitor had to install. The **`<embed>`** element was invented to hand a rectangle of the page to such a plug-in.

Those plug-ins have now disappeared from modern browsers. But the `<embed>` element is still part of HTML, still works for some files such as PDFs and SVG, and you will meet it in older code. This lesson explains what it does, what it cannot do, and **why you will usually choose something else.**

Drag the width, and turn the **type** off. The element is real, and the result shows its biggest weakness: when the browser cannot show the file, you get an **empty box** and no message.

`<embed>` is a **void element**: it has no closing tag and **no content**. There is nowhere to put fallback text or a download link inside it.

## Attributes

| Attribute | What it does | Notes |
| :-- | :-- | :-- |
| `src` | The address of the file to embed | Use `https://` |
| `type` | The MIME type of the file, such as `application/pdf` or `image/svg+xml` | Helps the browser choose how to show it |
| `width`, `height` | Size in pixels, with no units | Set both, or use CSS |

That is the whole official list. Any **other attributes** are passed along to whatever program handles the file. In the days of plug-ins, that is how you configured them. Today, there is almost nothing to pass to.

There is also **no `alt`**, no `loading`, no `sandbox`, and no `referrerpolicy`. You can add a `title` or an `aria-label` as a name for assistive technology, and CSS works on the element's box, but you cannot ask the browser to restrict what is inside.

### Do Not Trust `type` Alone

`type` is a hint. The browser also looks at the **`Content-Type` header** the server sends for the file. If they disagree, or if the file is something the browser will not show, you get an empty box. Make sure your server sends the right type for each file.

## `embed` vs `object` vs `iframe` vs `img`

<TabItem value="code" label="HTML Code" default>

<!-- A picture: use img -->
<img src="logo.svg" alt="CodeHarborHub logo" width="120" height="40">

<!-- A PDF, with a fallback: use object -->
<object data="guide.pdf" type="application/pdf" width="600" height="400">
  <a href="guide.pdf">Download the guide (PDF)</a>
</object>

<!-- A web page or widget: use iframe -->
<iframe src="https://example.com/widget" title="Widget" loading="lazy"></iframe>

<!-- embed: no fallback, no sandbox, no alt -->
<embed src="guide.pdf" type="application/pdf" width="600" height="400">

| | `img` | `object` | `iframe` | `embed` |
| :-- | :-- | :-- | :-- | :-- |
| Fallback content | `alt` text | **Yes**, inside the element | Text inside (rarely shown) | **None** |
| Text alternative | `alt` | Fallback content | `title` | Only `title` or `aria-label` |
| Can show a web page | No | Yes | **Yes, built for it** | Not intended |
| Lazy loading | `loading="lazy"` | No | `loading="lazy"` | No |
| Sandbox | n/a | No | **Yes** | **No** |
| Best for | Pictures, SVG used as a picture | PDFs and older embedded files | Pages, players, maps, widgets | Rarely; older code |

The honest summary: **in new code, you rarely need `<embed>`.** For a graphic, use `<img>` or inline SVG. For a PDF, `<object>` gives you a fallback link. For another page, `<iframe>` gives you `title`, lazy loading, and `sandbox`.

## Embedding a PDF

A PDF is the most common use today. Desktop browsers usually have a built-in viewer, so this works:

```html
<embed src="guide.pdf" type="application/pdf" width="600" height="400">
```

But think about the visitors for whom it does not:

- **Many phones and tablets** show nothing, or only a small preview, or just offer a download.
- Some browsers have **no built-in viewer** and download the file.
- A visitor with a **screen reader** or only a keyboard may find the viewer hard to use, and may get stuck inside it.
- You get **no fallback** for any of them.

You can ask the browser whether it has a viewer, on the supported browsers:

```js
if (navigator.pdfViewerEnabled) {
  // safe to show an inline viewer
} else {
  // show a plain download link instead
}
```

The simplest, kindest pattern is always: **a visible link to the PDF, with its size, next to or instead of the viewer.**

```html
<p><a href="guide.pdf">Download the guide (PDF, 1.2 MB)</a></p>
```

And if the content matters, offer an **HTML version** too. HTML is easier to search, translate, read on a phone, and use with assistive technology than most PDFs.

## Embedding SVG

An SVG file shown through `<embed>` is displayed as a separate document. Scripts inside the SVG can run, and the SVG can load other things. That is rarely what you want.

- For a **picture**, use `<img src="logo.svg" alt="…">`. It is safe (scripts do not run), cacheable, and has `alt`.
- For a graphic you want to **style or animate with your page's CSS and JavaScript**, use **inline SVG** (see [SVG](./svg)).

## A Note on Old Code

You may see older pages that wrap an `<embed>` inside an `<object>`, so that one works if the other does not, usually for Flash:

```html
<object data="movie.swf" type="application/x-shockwave-flash">
  <embed src="movie.swf" type="application/x-shockwave-flash">
</object>
```

Flash, Java applets, and similar plug-ins **no longer run in any current browser.** If you find code like this, the content must be rebuilt with video, SVG, canvas, or JavaScript. Do not try to bring plug-ins back.

## Accessibility at a Glance

- **Prefer elements with a text alternative:** `img` with `alt`, `object` with fallback content, `iframe` with `title`.
- **If you do use `embed`,** add a `title` or `aria-label`, and put a **visible text link** to the file next to it.
- **Give a text version** of anything important: an HTML page for a PDF, a data table for a chart.
- **Test with the keyboard.** A viewer inside the page can trap keyboard focus. Make sure a visitor can Tab out.
- **Make PDFs accessible** if you must publish them: tagged, with a title, language, headings, and alternative text for images.
- **Do not put essential information only in the embedded file.**
- **Set a size** so the page does not jump.

## Security and Privacy Notes

- **`<embed>` has no `sandbox`.** You cannot lock down what runs inside it. For anything you do not fully trust, use an `<iframe>` with `sandbox`.
- **Embedded files can carry active content.** An SVG can contain scripts, and a PDF can contain links and actions. Never embed a file uploaded by a visitor without checking it.
- **Serve the right headers.** Send the correct `Content-Type`, and add `X-Content-Type-Options: nosniff` so the browser does not guess a file's type.
- **Use `https://`.** An insecure embedded file in a secure page is blocked, or can be swapped by someone on the network.
- **Do not build `src` from user input.** A visitor could make your page show a harmful or private file. Use a fixed list of allowed files.
- **Remember that the file is public.** Anyone who sees the page can fetch the PDF or SVG directly.
- **Third-party embedded files** may report back to the other site (through the referrer, for example). See [Third-Party Content Security](./third-party-content-security).

## Global Audience Notes

- **Do not assume every device has a PDF viewer.** Many phones in many regions do not. A plain download link works everywhere.
- **PDFs are heavy.** Show the size ("1.2 MB") so visitors on slow or metered connections can choose.
- **Offer content in HTML,** which can be translated by the browser and read in right-to-left languages without special viewers.
- **Embedded PDF text may not follow the page's language settings.** Mark the language in the file, and name it in your link ("Guide (PDF, English)").
- **Make files available in more than one language** where you can, and name them clearly.

## Common Mistakes to Avoid

1. **Using `embed` where `img`, `object`, `iframe`, or `video` would do.**
2. **No visible link** to the file, so visitors with no viewer get an empty box.
3. **No `type`, or a wrong `type`,** so the browser does not know what to do.
4. **A wrong `Content-Type` header on the server.**
5. **No size,** so the page jumps.
6. **Expecting fallback content,** which `embed` does not have.
7. **Trying to bring back Flash or Java.**
8. **Embedding files from users, or from addresses you do not control,** without checks.
9. **Giving the only copy of important information** to a PDF.
10. **Forgetting a `title` or `aria-label`.**
11. **Trapping keyboard users** inside a viewer.
12. **Building `src` from user input.**

10. Bonus: write the plain HTML version of a short PDF, and compare how each works with a screen reader.

## Key Takeaways

- `<embed>` is a **void element** with `src`, `type`, `width`, and `height`, and **no fallback content**.
- It came from the **plug-in era.** Flash, Java applets, and similar plug-ins no longer run.
- Today it can still show **PDFs and SVG files**, but better elements usually exist.
- Use **`img`** for pictures, **`object`** for PDFs with a fallback, **`iframe`** for pages and widgets, and **`video`** or **`audio`** for media.
- Always provide a **visible link** and a **text version** of important content.
- `embed` has **no sandbox, no `alt`, and no lazy loading.** Treat what it loads with care.
- Send the right `Content-Type`, use HTTPS, and never build `src` from user input.
- Do not assume a PDF viewer on every device.
