        inner: window.innerWidth + " × " + window.innerHeight,

        screen: window.screen.width + " × " + window.screen.height,

Imagine opening a website on your phone, and seeing a tiny copy of the desktop page: text too small to read, and you have to pinch and drag to find anything. That experience is common on pages without the **viewport** tag, and it is the reason this one line of HTML exists.

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

In this lesson you will learn what it means, why zooming must always stay on, and how it works together with your CSS.

## What Is a Viewport?

The **viewport** is the window onto your page: the part of the page you can see right now. On a desktop, it is the browser window. On a phone, there are really two:

| Term | Meaning |
| :-- | :-- |
| **Layout viewport** | The width the browser uses to lay out your page. CSS percentages and media queries use this |
| **Visual viewport** | The part the visitor can currently see. It shrinks when they pinch-zoom in, or when the on-screen keyboard appears |

Early phone browsers faced a problem: most websites were built for wide desktop screens. So phones **pretended** the screen was about **980 pixels wide**, laid out the page that way, then shrank the result to fit. That kept old sites readable-ish, but it makes modern, responsive sites look wrong.

The viewport tag is how you tell the phone: *"This page is built for small screens. Do not pretend."*

## The Two Settings You Need

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

| Part | Meaning |
| :-- | :-- |
| `width=device-width` | Make the layout width equal to the real screen width, measured in CSS pixels |
| `initial-scale=1` | Start at normal size, with no zoom in or out |

**CSS pixels** are not the same as the physical dots on the screen. A modern phone may have a 1170-dot-wide screen, and still report about 390 CSS pixels, so that text stays readable. Your CSS works in CSS pixels.

## Other Settings (and Which to Avoid)

You can add more properties. Some are useful. Some are harmful.

| Property | Example | Advice |
| :-- | :-- | :-- |
| `width` | `device-width` or `600` | Use `device-width`. A fixed number is rarely right |
| `initial-scale` | `1` | Keep at `1` |
| `minimum-scale` | `1` | Not needed |
| `maximum-scale` | `5` | If you must set it, keep it **at least 2 or higher.** Never `1` |
| `user-scalable` | `no` | **Never.** It blocks zooming |
| `viewport-fit` | `cover` | Useful for full-screen designs on notched phones, with safe-area padding (see below) |
| `interactive-widget` | `resizes-content` | Controls how the on-screen keyboard changes the layout. Support is newer and varies, so test |

### Why Blocking Zoom Is Harmful

```html
<!-- Do not do this -->
<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no, maximum-scale=1">
```

People zoom for many reasons: low vision, small text, a bright screen, a hard-to-read font, or just looking at a photo more closely. Taking that away makes your page **unusable** for some visitors, and it goes against the Web Content Accessibility Guidelines, which expect text to be resizable up to 200 percent without loss of content.

Some browsers now **ignore** attempts to block zoom for this reason, but you cannot rely on that. Simply do not write it.

:::danger Never disable zoom
Do not add `user-scalable=no`. Do not set `maximum-scale=1`. If a layout "breaks" when zoomed, fix the layout, not the zoom.
:::

## The Viewport Tag Is Only Half the Job

The tag makes the layout width equal to the screen width. Your **CSS** must then adapt to that width:

```css
/* Flexible images and media */
img, video { max-width: 100%; height: auto; }

/* Mobile-first: base styles are for small screens */
.cards { display: grid; gap: 1rem; }

/* Wider screens get more columns */
@media (min-width: 600px) {
  .cards { grid-template-columns: repeat(2, 1fr); }
}
@media (min-width: 900px) {
  .cards { grid-template-columns: repeat(3, 1fr); }
}
```

Tips:

- **Design mobile first.** Write the small-screen styles first, then add rules for wider screens with `min-width`.
- **Use relative units** (`rem`, `%`, `fr`, `ch`) rather than fixed pixel widths.
- **Avoid horizontal scrolling.** Wide tables, long words, and fixed-width elements are common causes.
- **Make touch targets big enough:** at least about 44 by 44 CSS pixels is a common guideline for buttons and links.
- **Use `100dvh`** (dynamic viewport height) instead of `100vh` for full-height sections, because phone address bars appear and disappear, and `100vh` can be taller than what you can see.

## Notches and Safe Areas

Some phones have a notch, rounded corners, or a home bar that covers part of the screen. By default, browsers keep your page inside the **safe area**. If you want content to run edge to edge, opt in:

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

Then add padding so text never hides behind the notch:

```css
body {
  padding-left: env(safe-area-inset-left);
  padding-right: env(safe-area-inset-right);
  padding-bottom: env(safe-area-inset-bottom);
}
```

Only use `viewport-fit=cover` if you are ready to handle those insets.

## Text Size and Zoom on Inputs

A few extra mobile details:

- Keep body text at **16 pixels or larger.** Some mobile browsers zoom in automatically when a visitor taps a form field with text smaller than 16 pixels, which can be disorienting.
- Use `rem` for font sizes, so the visitor's own text-size setting is respected.
- Test with the browser's text size set to large.

## Good Habits

1. **Always include `width=device-width, initial-scale=1`.**
2. **Never block zoom.**
3. **Build mobile first,** then enhance for larger screens.
4. **Use relative units and flexible images.**
5. **Test on a real phone,** and in your browser's device mode.
6. **Test at 200 percent zoom,** and at about 320 CSS pixels wide.
7. **Use `dvh` units** for full-height layouts on phones.
8. **Respect safe areas** if you use `viewport-fit=cover`.

## Accessibility Checklist

- [ ] The viewport tag is present, and **does not** disable zoom.
- [ ] The page works at **320 CSS pixels** wide without sideways scrolling (except for things like data tables or maps that need two dimensions).
- [ ] Text can be enlarged to 200 percent without loss of content.
- [ ] Touch targets are large enough, with space between them.
- [ ] Fixed or sticky bars do not cover content when zoomed.
- [ ] The layout still works in both portrait and landscape.
- [ ] Orientation is not locked without a real need.

## Security and Privacy Notes

- **The viewport tag itself is harmless,** but what it controls is not just visual: a page that blocks zoom makes it harder for people to **read warnings, consent text, and security prompts,** and to notice details in a web address.
- **Clickjacking and tiny controls:** with a fixed, tiny layout, tapping the wrong thing is easy. Large targets with space between them reduce accidental taps on buttons such as "Delete" or "Pay".
- **Do not use viewport data to track people.** Combining screen size, pixel ratio, and other values can contribute to **fingerprinting.** Use these values for layout, and avoid collecting them without a reason.
- **Safe-area use:** make sure important controls, such as a consent button, are not hidden under a notch or home bar.

## Global Audience Notes

- **Many people in the world use phones as their only computer,** often small, older, or low-cost models. The viewport tag is not optional for them.
- **Test narrow widths,** such as 320 pixels, and with larger system text, which is common among older users.
- **Right-to-left and long-word languages** may need more room. Use flexible layouts, and let text wrap.
- **Translations can be 30 percent longer,** which can break fixed-width buttons.
- **Do not rely on hover.** Touch screens have none.
- **On slow networks,** a mobile-first page that loads small images first is faster and cheaper to use.

## Common Mistakes to Avoid

1. **No viewport tag,** so phones show a tiny desktop page.
2. **`user-scalable=no`.**
3. **`maximum-scale=1`.**
4. **A fixed pixel width,** such as `width=1024`.
5. **Forgetting responsive CSS,** so the tag does not help.
6. **Elements wider than the screen,** causing sideways scrolling.
7. **Using `100vh`** for full-height sections on phones.
8. **`viewport-fit=cover` without safe-area padding.**
9. **Tiny tap targets.**
10. **Text smaller than 16px in inputs.**
11. **Testing only on a desktop browser.**
12. **Two viewport tags** with conflicting values.

4. Write a mobile-first stylesheet with one `min-width` media query.

## Key Takeaways

- Without a viewport tag, phones lay out your page at about **980 pixels** and shrink it.
- Use **`<meta name="viewport" content="width=device-width, initial-scale=1">`** on every page.
- **Never block zoom:** no `user-scalable=no`, no `maximum-scale=1`.
- The tag only sets the width. **Responsive CSS** does the rest.
- Build **mobile first,** use relative units, and test on real devices at 320 pixels and 200 percent zoom.
- Use **`dvh`**, safe-area insets, and large touch targets for a good phone experience.
- Be careful with screen data, to avoid fingerprinting.
