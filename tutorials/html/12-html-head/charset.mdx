Have you ever opened a web page and seen text like **cafÃ©** instead of **café**, or rows of **�** and empty boxes? That is a **character encoding** problem, and it is one of the oldest bugs on the web. It happens when the browser reads a page using different rules from the ones used to save it.

The fix is one short line in your head: `<meta charset="utf-8">`. In this lesson you will learn **why** it works, so you can recognise and prevent encoding bugs for good.

## Computers Only Store Numbers

A computer file is a long list of **bytes**: numbers from 0 to 255. Letters are not stored. Instead, there is an agreement: "number 65 means the letter A". The agreement is called a **character encoding**.

Long ago, every region made its own agreement. One encoding for Western Europe, one for Russian, one for Japanese. The same byte meant **different letters** in each of them. A file saved with one agreement and read with another turns into nonsense.

```
Bytes:  63 61 66 c3 a9
Read as UTF-8:         café
Read as windows-1252:  cafÃ©     <- same bytes, wrong agreement
```

## Unicode and UTF-8

**Unicode** is one big catalogue that gives every character in every writing system its own number, called a **code point**, written like `U+00E9` for é. It covers Latin, Devanagari, Arabic, Chinese, Japanese, Korean, mathematics, emoji, and much more. Unicode says **which number** each character has.

**UTF-8** is the way of **writing those numbers as bytes**. It is the encoding you should use for the web:

| Character type | Bytes in UTF-8 | Example |
| :-- | :-- | :-- |
| Basic English letters, digits, punctuation (ASCII) | 1 | `A`, `7`, `?` |
| Accented letters, Greek, Cyrillic, Hebrew, Arabic | 2 | `é`, `Ж`, `ع` |
| Most Indian scripts, Thai, Chinese, Japanese, Korean, the rupee sign | 3 | `हि`, `日`, `₹` |
| Emoji and rare characters | 4 | `😀` |

Why UTF-8 won:

- It can represent **every** character in Unicode.
- Plain English text looks **identical** to the older ASCII, so old files keep working.
- It is **compact** for English, and still handles every language.
- It is the **default recommendation** of the HTML standard, and nearly the whole web uses it.

## Declaring the Encoding: meta charset

```html
<meta charset="utf-8">
```

Rules:

1. Put it **inside `<head>`**, as early as possible.
2. It must appear **within the first 1024 bytes** of the file. A very long comment or script above it can push it out of range.
3. **Only one** such tag per page.
4. The value is **not case-sensitive.** `UTF-8` and `utf-8` both work.
5. It must **match how the file was really saved.** The tag is a label, and a wrong label does not convert anything.

You may see an older form:

```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8">
```

It does the same job but is longer. Use the short form.

## Who Wins? The Order of Priority

A browser can learn the encoding from several places. In order, from strongest to weakest:

1. A **byte order mark (BOM)** at the very start of the file (a few special bytes some editors add)
2. The **`charset` in the HTTP `Content-Type` header,** sent by the server
3. The **`<meta charset>`** tag in the page
4. A **guess** by the browser, based on the bytes and on its language settings

This means that if your **server header says one thing** and your **meta tag says another,** the header usually wins, and your page may break even though the HTML looks right. When you see mojibake, check the server setting, as well as the page.

:::info Always declare it
If there is no declaration, the browser guesses, and different browsers guess differently. A page may look right on your computer, but wrong for a visitor in another country. Declare the encoding every time.
:::

## Fixing Garbled Text: A Checklist

When text looks wrong, check these in order:

1. **Is the file really saved as UTF-8?** In your code editor, look at the status bar, or use "Save with Encoding".
2. **Is `<meta charset="utf-8">` present,** and near the top of the head?
3. **Does the server send a different `charset`** in its `Content-Type` header? Look in the browser's Network tab.
4. **Was the text damaged before it reached the page?** Check your database, your import scripts, and your copy-and-paste path.
5. **Did something convert it twice?** Text such as `Ã©` often means UTF-8 bytes were read as another encoding and then saved again. Once saved like that, you must repair the text, not just the label.

| What you see | Usual cause |
| :-- | :-- |
| `Ã©`, `â‚¹`, `Ð¿` in place of normal letters | UTF-8 text read as windows-1252 |
| `?` in place of letters | Text was converted into an encoding that does not have those characters, and the loss is permanent |
| `�` | Bytes that are not valid in the encoding being used |
| Empty boxes | The encoding is right, but **no font** has that character |

The last one is different: the text is correct, but the device has no font with that symbol. It is a **font** problem, not an encoding problem.

## HTML Entities: Another Way to Write Special Characters

You can also write a character as an **entity** that uses only plain ASCII. It survives any encoding:

```html
<p>&copy; 2026 &mdash; Price: &euro;20, &#8377;1500, &#x1F600;</p>
```

| Form | Example | Result |
| :-- | :-- | :-- |
| Named | `&copy;` | © |
| Decimal number | `&#8377;` | ₹ |
| Hexadecimal number | `&#x1F600;` | 😀 |

Entities are essential for the characters that have special meaning in HTML: `&lt;` for `<`, `&gt;` for `>`, `&amp;` for `&`, and `&quot;` for a quote inside an attribute.

But for everyday text, **write the real character and use UTF-8.** It is easier to read and maintain than a page full of numbers.

## Other Places Where Encoding Matters

| Place | What to do |
| :-- | :-- |
| **Your editor** | Save files as UTF-8 (without a BOM, if you can choose) |
| **The web server** | Send `Content-Type: text/html; charset=utf-8` |
| **CSS files** | Add `@charset "utf-8";` as the very first line if the file has non-ASCII characters and the server does not say |
| **JavaScript files** | Serve as UTF-8. Modules always read UTF-8 |
| **Databases** | Use a full UTF-8 setting. In MySQL, that means `utf8mb4`, not the older `utf8`, which cannot store emoji |
| **Forms** | Browsers send form data as UTF-8 by default. You can check with `accept-charset="utf-8"` on the form |
| **URLs** | Non-ASCII characters in addresses are converted to `%`-codes based on UTF-8 |
| **Email, CSV, and other files** | State the encoding, or open the file as UTF-8 explicitly |

## Good Habits

1. **Use UTF-8 for everything:** files, server, database, forms.
2. **Write `<meta charset="utf-8">` as the first thing in your head.**
3. **Do not rely on the browser's guess.**
4. **Check the server header** when the tag looks right but the text is wrong.
5. **Test with real data** in several scripts: accented, Indic, Arabic, CJK, and emoji.
6. **Use entities** for `<`, `>`, and `&` in text.
7. **Keep the tag within the first 1024 bytes.**
8. **Do not convert text between encodings** in the middle of your pipeline.

## Accessibility Checklist

- [ ] Every character in the page, including the `<title>`, displays correctly.
- [ ] Screen readers receive real text, not garbled symbols or stand-in question marks.
- [ ] Symbols used as icons also have a **text** alternative.
- [ ] Emoji used in headings or buttons are **optional extras,** not the only way to understand the content.
- [ ] Text in other languages has the right `lang` attribute.
- [ ] Right-to-left text displays and reads in the right order.

## Security and Privacy Notes

- **Always declare the encoding.** Old attacks used pages with no declared encoding, so a browser would guess an unusual one (such as UTF-7), and read harmless-looking text as active script. A declared UTF-8 page closes that door.
- **Validate input as UTF-8** on the server. Reject or clean invalid byte sequences, instead of passing them along.
- **Look-alike characters** from different scripts (for example, a Cyrillic "а" that looks like a Latin "a") can be used for tricks in names and addresses. Be careful when you compare, show, or trust user names and links.
- **Invisible and direction-control characters** can hide in text and code, and change what a reader sees. Review pasted code and user content, and consider stripping them from fields such as user names.
- **Do not trust the byte length of a string** as its character length. A limit measured in bytes can cut a character in half and produce invalid text.
- **Do not use a conversion function on text** that may already be in the target encoding, because double conversion damages it.

## Global Audience Notes

- **UTF-8 is what lets one page serve the world.** There is no good reason to choose a regional encoding for a new site.
- **Allow real names.** Do not restrict name fields to English letters, because many names include accents, other scripts, apostrophes, and spaces.
- **Sorting, upper and lower case, and length** differ by language. Do not assume one letter equals one byte, or that every language has upper and lower case.
- **Fonts matter.** An encoding can be perfect while the font lacks the characters. Use a font stack that covers your audience's scripts, or load a suitable web font.
- **Emoji look different** on different devices, and new ones may not show on older systems. Do not depend on them for meaning.
- **Right-to-left text** is stored in logical order, and the browser draws it correctly. Mark the direction with `dir`.
- **JavaScript string lengths** count UTF-16 units, not visible characters, so `"😀".length` is 2. Use `Array.from(text)` or `Intl.Segmenter` to count what people see.

## Common Mistakes to Avoid

1. **No charset declaration.**
2. **Saving the file in one encoding but declaring another.**
3. **Putting `<meta charset>` after a long comment or script** (beyond 1024 bytes).
4. **A server header that disagrees with the tag.**
5. **Using MySQL `utf8` instead of `utf8mb4`.**
6. **Converting text twice,** and creating permanent damage.
7. **Mistaking a missing font** for an encoding problem.
8. **Using two charset tags.**
9. **Limiting names or text to ASCII.**
10. **Counting bytes when you mean characters.**
11. **Using entities everywhere** when plain UTF-8 text would be clearer.
12. **Testing only with English text.**

## Key Takeaways

- A **character encoding** is the agreement that turns bytes into letters.
- **Unicode** numbers every character, and **UTF-8** writes those numbers as bytes. Use it everywhere.
- Declare it with **`<meta charset="utf-8">`**, first in the head, within the first 1024 bytes.
- The **BOM, then the server header, then the meta tag, then a guess** decide which encoding is used.
- Garbled text means the **file, server, and tag disagree**, or the text was damaged earlier.
- Entities such as `&amp;` are needed for `<`, `>`, `&`, and quotes, but plain UTF-8 text is best for everything else.
- Always declare the encoding, validate input as UTF-8, and test with many scripts.
